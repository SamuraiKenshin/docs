1.1 What system design is

From "it works on my machine" to "it works for a million people at once."

About 12 minutesLevel: beginner

When you write a C# class, you decide what methods it has, what data it holds, and how it talks to other classes. That's software design, and it happens inside one program.

System design is the same kind of thinking, one level up. Instead of classes, the pieces are whole programs and machines: web servers, databases, caches, queues, load balancers. Instead of method calls, they talk over a network. System design is deciding:

  • What the pieces are: which services, which databases, which caches.
  • How they talk: HTTP calls, messages on a queue, events on a stream.
  • Where data lives: which database, how many copies, in which regions.
  • How it behaves under pressure: when traffic triples, when a server dies, when a whole data center goes dark.

Why it matters: the same app at three sizes

Imagine BlueHarbor's tracking API as a single ASP.NET Core app with one SQL database on one virtual machine.

UsersWhat happensWhat you need to think about
100Everything is fast. One server is mostly idle.Almost nothing. Ship it.
100,000The database CPU sits at 90% during the morning in Europe. Deploys cause 30 seconds of errors. A disk failure would lose a day of data.Caching, more app servers behind a load balancer, backups and a replica, zero-downtime deploys.
10,000,000Customers in Asia see slow pages. Partner carriers push millions of events an hour. One bad dependency takes the whole site down.Multiple regions, queues for ingestion, splitting data across databases, isolating failures, observability.

The code for "look up a container's events" barely changes across these three rows. Everything around it changes. That surrounding structure is the system design.

Analogy: a dock versus a container port

One dock with one crane works fine for a fishing village. A port handling 15 million containers a year needs gates that check trucks in (load balancers), a yard to stage boxes (caches and storage), many cranes working in parallel (app servers), a berth schedule so ships don't collide (queues), and backup power so one failure doesn't stop everything (redundancy). The crane itself is the same machine. The port is the design.

There are no right answers, only trade-offs

This is the most important idea in the whole guide. Every design decision gives you something and costs you something. A senior engineer isn't someone who knows the "correct" architecture. It's someone who can say, clearly, what they're giving up and why that's acceptable here.

In the real world

Most production systems didn't start as clever designs. They started as one app and one database, and each scaling problem was solved when it showed up. Good system design is often about not building for 10 million users on day one, but leaving room to get there. Over-engineering early is as common a mistake as under-engineering.

Interview questions

JuniorWhat's the difference between software design and system design?▶

Software design is about structure inside one program: classes, interfaces, patterns like Strategy or Repository. System design is about structure across programs and machines: services, databases, caches, queues, and the network between them.

The key difference is what can fail. Inside one process, a method call basically always arrives. Across a network, calls can be slow, lost, duplicated, or reach a server that just crashed. System design is largely about designing for that uncertainty.

Likely follow-up: "Give an example of something that's easy inside one process but hard across two services." A good answer: a transaction that updates two tables atomically is easy in one database; updating two services' databases atomically needs patterns like sagas or the outbox (Part 4).
MidWhy do interviewers care more about trade-offs than about the "right" architecture?▶

Because there isn't a right architecture in the abstract. A design that's perfect for a bank ledger (strong consistency, every write confirmed) would be wasteful for a social feed (where a few seconds of staleness is fine and speed matters more).

Talking about trade-offs shows you understand why a design works, which means you can adapt it when requirements change. Naming the cost of your choice ("this cache means status can be up to 30 seconds stale; that's fine because carriers only push updates every few minutes anyway") is a strong senior signal.

Likely follow-up: "Pick one decision in a system you've built and tell me what it cost you."
SeniorYou inherit a system that "works." How do you decide what to redesign first?▶

Start from evidence, not taste. I'd look at three things:

  1. Where it hurts today: incidents, on-call pages, slow endpoints at p99, the deploy process. Recurring incidents point at the real weak spots.
  2. Where it will hurt next: growth projections versus current headroom. If the database is at 60% CPU and traffic grows 2x a year, that's a deadline.
  3. Single points of failure: one database with no replica, one region, one shared service everything calls.

Then I'd rank by risk times likelihood, prefer incremental changes (add a replica, add a cache, extract one module) over rewrites, and make sure observability is in place first, because you can't safely change what you can't measure.

Likely follow-up: "When would a rewrite be the right call?" Rarely: when the platform is unsupported, when the core data model is fundamentally wrong for the business, or when incremental change costs more than starting over. Even then, use a strangler approach that replaces one piece at a time.

1.2 Requirements and the "-ilities"

Before drawing a single box: what must the system do, and how well must it do it?

About 20 minutesLevel: beginner2 interactive tools

Every design starts with requirements, and they come in two kinds:

  • Functional requirements describe what the system does. They're features: "a shipper can look up a container by its number."
  • Non-functional requirements (NFRs) describe how well it does it: "lookups return in under 300 ms for 99% of requests, and the service is up 99.9% of the time."

Functional requirements decide what you build. Non-functional requirements decide how you build it. Two systems with identical features can need completely different architectures because their NFRs differ.

Worked example: BlueHarbor's tracking platform

Notice how much the right column tells you. "Never lose a confirmed event" means you need durable storage with replicas. "Bursts of 5,000 per second" suggests a queue to absorb spikes. "Up to 5 minutes stale" gives you permission to cache aggressively. The NFRs are already sketching the architecture.

What happens when you chain dependencies

If a request needs every component to work, their availabilities multiply. Redundant copies work the other way: the system is only down if all copies are down at once.

The chain result is the lesson: every dependency you add lowers your ceiling. An API that calls four services, each at 99.9%, can't be better than about 99.6% unless something is redundant. This is why later parts spend so much time on redundancy, timeouts, fallbacks, and circuit breakers.

Latency, and why averages lie

Latency is the time one request takes. The trap is measuring it with an average. A few very slow requests hide inside an average, but they're exactly the ones your users complain about. Engineers use percentiles instead:

  • p50 (median): half of requests are faster than this. The "typical" experience.
  • p95: 95% are faster. 1 in 20 requests is slower.
  • p99: 99% are faster. The "tail." 1 in 100 is slower.

SLI, SLO, SLA and the error budget

Three acronyms that sound alike but mean different things. Getting them right is a common interview check.

  • SLI (service level indicator): a measurement. "The percentage of tracking lookups that returned successfully in under 300 ms."
  • SLO (service level objective): your internal target for that measurement. "99.5% of lookups, measured over 30 days."
  • SLA (service level agreement): a promise to customers with consequences, usually money back. "If availability drops below 99.9% in a month, you get a 10% credit." SLAs are set looser than SLOs so you have a safety margin.

The error budget is what's left over: with a 99.5% SLO, 0.5% of requests are allowed to fail or be slow. If you're well within budget, the team can ship faster and take risks. If the budget is burned, you slow down and fix reliability. It turns "how reliable should we be?" from an argument into a number.

In .NET: measuring your SLIs

ASP.NET Core already emits a request-duration histogram (http.server.request.duration) through System.Diagnostics.Metrics. You export it with OpenTelemetry and add your own business metrics, like how stale tracking data is. Part 5 covers the full observability stack; this is the minimum.

Constraints, assumptions, and what's out of scope

Requirements also include things you can't change and things you choose not to do. Writing them down prevents arguments later.

  • Constraints: "Must run on Azure," "the team knows .NET and SQL Server," "partners send EDI files, not JSON."
  • Assumptions: "Reads outnumber writes about 10 to 1," "most lookups are for containers that moved in the last 30 days."
  • Out of scope: "No customs filing in version 1," "no mobile push notifications yet."

Common pitfalls

  • Vague NFRs. "It should be fast" can't be designed for or tested. "p99 under 300 ms at 2,000 requests per second" can.
  • Gold-plating. Asking for five nines when the business would be fine with three. Each nine costs roughly 10x more effort.
  • Forgetting the read/write mix. A system that's 99% reads is designed very differently from one that's 50/50.
  • Ignoring data growth. A table that's fine at 1 million rows can be a problem at 2 billion. Ask about retention early.

Interview questions

JuniorWhat's the difference between functional and non-functional requirements? Give two examples of each.▶

Functional requirements are features, what the system does: "users can book a container slot," "users can download a bill of lading." Non-functional requirements are qualities, how well it does them: "booking confirmation in under 2 seconds," "99.9% availability."

A useful test: if you removed it, would a feature be missing (functional) or would the same feature just be worse (non-functional)?

Likely follow-up: "Which kind changes the architecture more?" Usually non-functional. The same features can be one server or a global multi-region system depending on scale, latency, and availability needs.
MidWhy measure p99 latency instead of the average?▶

Averages hide the tail. If 98 requests take 20 ms and 2 take 2 seconds, the average is about 60 ms, which looks fine, but 2% of users wait 2 seconds. Percentiles show the experience of real slices of users.

Tail latency also compounds: a page making 20 calls has roughly an 18% chance of hitting at least one p99-slow call. And the slowest requests often come from your busiest, most valuable customers (those with the most data).

Likely follow-up: "How would you reduce p99 without changing p50?" Find what makes those requests slow (cold cache, GC pauses, a slow dependency, lock contention), then fix it with timeouts, caching, hedged requests, or splitting heavy work off the request path.
MidYour API calls three services, each 99.9% available. What's the best availability you can promise?▶

If all three are required, multiply: 0.999 × 0.999 × 0.999 ≈ 0.997, so about 99.7%, and that's before counting your own service's failures. That's roughly 26 hours of potential downtime per year instead of 8.8.

To do better you remove the hard dependency: cache the dependency's data, provide a fallback (show the last known vessel ETA), make the call asynchronous, or run redundant copies so one failure doesn't fail the request.

Likely follow-up: "Two redundant copies at 99% each, what's the combined availability?" 1 − (0.01 × 0.01) = 99.99%, assuming failures are independent. Then they'll ask when that assumption breaks: both copies in the same rack, region, or sharing a bad deploy.
SeniorHow would you set an SLO for a new tracking API, and what does the error budget let the team do?▶

Start from user experience, not technology. Talk to the people who use it: shippers checking a few containers a day tolerate occasional slowness; a freight forwarder's system polling 50,000 containers needs consistency. Pick SLIs that reflect that: success rate, latency at p99, and freshness (event-to-queryable lag).

Set the first SLO from measured reality (what we achieve today), slightly below it, then tighten over time. Set the external SLA looser still. A 30-day rolling window is common.

The error budget makes reliability a shared decision. With budget left, teams ship features and run experiments. When it's burned, a pre-agreed policy kicks in: freeze risky launches, prioritize reliability work. It aligns product and engineering on one number instead of opinions.

Likely follow-up: "What if the dependency you call has a lower SLO than yours?" You either can't promise yours, or you design around it: caching, async processing, graceful degradation.

On a fresh connection, more than half the time goes into setting up the conversation (DNS, TCP, TLS) before a single byte of your request is sent. Your C# code and database account for only a few milliseconds. This is the first big lesson of system design: the network usually dominates, and round trips are the currency you spend.

The handshakes, slowed down

A round trip time (RTT) is how long it takes a message to go to the server and a reply to come back. On mobile, 60–100 ms is common; between continents, 150 ms or more. Count the arrows that have to cross before data arrives:

This is why connection reuse matters so much. Browsers and HttpClient keep connections open (keep-alive) so the second request skips straight to sending data. It's also why CDNs and edge servers help: they terminate TCP and TLS close to the user, so the expensive round trips are short ones.

Where this sits in the OSI model

You already know Layer 7 from your earlier study. System design mostly lives in three layers, and one distinction (L4 vs L7) comes up constantly in later parts:

Inside the app server: the ASP.NET Core pipeline

When the request reaches your server, Kestrel (ASP.NET Core's built-in web server) parses it, and it flows through the middleware pipeline: a chain of components where each can act on the request, pass it on, and act on the response on the way back. Order matters: authentication must run before authorization, and the exception handler must be first so it can catch everything after it.

The other direction: your app calling other services

Your service is also a client when it calls other APIs, like a partner's vessel schedule service. Everything above applies in reverse, and there's a classic .NET trap here.

Common pitfalls

  • Chatty clients. A mobile screen that makes 15 sequential API calls pays 15 round trips. Batch them into one endpoint designed for that screen, or run them in parallel.
  • Blaming the code first. Your server logs say 20 ms, but users see 900 ms. The gap is DNS, handshakes, distance, and payload size, none of which shows up in server-side timing.
  • Huge responses. Returning 3 MB of JSON when the screen shows 20 rows. Paginate, select only needed fields, and enable response compression.
  • Long DNS TTLs during migrations. If your DNS record says "cache me for a day," moving to a new load balancer takes a day to reach everyone.

Interview questions

JuniorWhat happens when you type a URL into a browser and press Enter?▶

A strong answer walks the layers in order:

  1. The browser checks its caches, then the OS cache, for the domain's IP.
  2. If not cached, a DNS resolver looks it up (root, then the TLD like .com, then the domain's authoritative server) and returns an IP, often a load balancer or CDN edge.
  3. The browser opens a TCP connection (3-way handshake), then a TLS handshake to encrypt it. With HTTP/3, QUIC does both in one step.
  4. It sends the HTTP request. A load balancer picks a healthy server; the server's framework runs middleware and the handler, which may hit caches and databases.
  5. The response comes back; the browser parses HTML, fetches CSS/JS/images (often from a CDN), and renders. The connection stays open for reuse.
Likely follow-up: "Which of those steps would you optimize first for a user in another continent?" The round trips: put TLS termination and static content at an edge/CDN close to them, and reduce the number of requests.
MidWhat's the difference between an L4 and an L7 load balancer?▶

An L4 load balancer works at the transport layer: it sees IPs and ports and forwards TCP/UDP connections without reading their contents. It's very fast and protocol-agnostic, but it can't route by URL or header.

An L7 load balancer understands HTTP. It can route /api/bookings to one service and /api/tracking to another, terminate TLS, add headers, do sticky sessions by cookie, rate limit, and retry. It costs more CPU per request and must decrypt traffic to read it. In .NET, YARP is an L7 reverse proxy library.

Likely follow-up: "Where would you use each?" L4 in front of non-HTTP protocols or as the first tier for raw throughput; L7 for HTTP APIs that need path routing, auth, or canary releases. Many systems use both: L4 at the edge spreading load across L7 proxies.
MidWhy can creating a new HttpClient for every request break a .NET service under load?▶

Each new HttpClient (with its own handler) opens new connections. When it's disposed, the sockets stay in TIME_WAIT for a while at the OS level. Under high load you run out of available ports: "socket exhaustion." You also pay a fresh TCP and TLS handshake on every call, adding latency.

The fix is reusing handlers: IHttpClientFactory (named or typed clients), or a single long-lived client with SocketsHttpHandler.PooledConnectionLifetime set so connections are recycled and DNS changes are noticed.

Likely follow-up: "Then why not one static HttpClient forever?" Without a connection lifetime, it can keep using a stale IP after a DNS change, for example after a failover.
SeniorUsers in Singapore say the API is slow, but your server metrics show 20 ms. Where's the time going, and what do you do?▶

Server-side metrics only measure from "request received" to "response written." The rest is invisible to them: DNS, TCP and TLS handshakes, and transfer time over a roughly 160 ms RTT from Singapore to a European region. A cold request can easily spend 500+ ms in the network.

I'd confirm with client-side measurements (real user monitoring, or synthetic probes from Singapore), then attack round trips in order of impact:

  • Terminate TLS near the user with a CDN or global edge (e.g., Azure Front Door), which keeps warm connections back to the origin.
  • Cache read-heavy, cacheable responses at the edge.
  • Reduce request count and payload size (batching, compression, pagination).
  • If it's still not enough, deploy read replicas or a full region in Asia, which brings consistency and data-residency trade-offs (Parts 2 and 4).
Likely follow-up: "What does a second region cost you?" Data replication lag, conflict handling if both regions write, double the infrastructure, and more complex deploys and incident response.

The handful of numbers that let you judge a design in your head, and how to size a system on the back of an envelope.

You don't need exact numbers to design well. You need the right order of magnitude. Is this operation nanoseconds, microseconds, or milliseconds? That difference is a factor of a thousand each time, and it decides whether a design is fine or hopeless.

    Five rules that fall out of the ladder

    1. Memory is roughly 1,000x faster than an SSD read, and an SSD read is roughly 1,000x faster than a round trip across an ocean. Keep hot data in memory (caches) and close to users.
    2. Round trips are expensive. One query returning 100 rows beats 100 queries returning one row each (the N+1 problem).
    3. Distance can't be optimized away. Light in fiber covers about 200 km per millisecond. Europe to Singapore will always cost over 100 ms per round trip. Move data closer instead.
    4. Sequential beats random. Reading data that's stored together is far faster than jumping around. This is why indexes and append-only logs matter.
    5. Inside one data center, the network is fast enough to be practical. That's what makes splitting a system across machines workable at all.

    Back-of-the-envelope estimation, step by step

    Estimation answers "how big is this, really?" so you pick the right architecture. Being within 2–3x is plenty. The method:

    1. Users and actions: daily active users (DAU) and what each does per day.
    2. Average rate: requests per day ÷ 86,400 = queries per second (QPS).
    3. Peak rate: multiply by a peak factor (2–10x). Traffic is never flat.
    4. Split reads and writes: they're scaled with different tools.
    5. Storage: writes per day × record size × retention × number of copies.
    6. Bandwidth: requests per second × response size.
    7. Sanity check: does the answer fit on one machine? That's the real question.

    Now load "Reefer telemetry": 500,000 refrigerated containers reporting temperature every 15 minutes is 48 million writes a day, about 560 per second, and constant. That's 16x the write rate of all the tracking events combined. One feature completely changes the storage design: it needs a write-optimized, time-series-friendly store and probably a stream to absorb it. You'll design exactly this in Part 7.

    Little's Law: from throughput to concurrency

    One formula connects rate and latency, and it's surprisingly practical:

    requests in flight = arrival rate × time each request takes

    At 1,160 requests per second with 50 ms per request, about 58 requests are in progress at any moment. If each holds a database connection for 20 ms, you need about 1,160 × 0.02 ≈ 23 connections busy on average, so a pool of 100 has headroom. But if a slow query makes that 500 ms, you suddenly need 580 connections, the pool runs dry, and requests start queueing and timing out. Latency spikes turn into capacity problems.

    Common pitfalls

    • Forgetting the peak. Systems fail at peak, not on average. Logistics has strong seasonality: pre-holiday shipping and the rush before Lunar New Year factory closures.
    • Forgetting replication and indexes. Indexes often add 30–100% to table size, and every replica is a full copy.
    • False precision. "1,157.4 QPS" signals you've missed the point. Round aggressively and state assumptions.
    • Connection pool math across instances. Scaling out app servers multiplies connections to the database, which can exhaust its limit.

    1.5 Scaling and stateless services

    Bigger machines or more machines? And what has to change in your ASP.NET Core app before you can run more than one copy.

    About 25 minutesLevel: intermediate1 simulator

    When one server can't keep up, you have two options:

    • Vertical scaling (scale up): give the server more CPU and memory. No code changes, but there's a ceiling, prices climb steeply near the top, and it's still one machine that can fail.
    • Horizontal scaling (scale out): run more copies of the server behind a load balancer. No hard ceiling, and losing one copy isn't fatal, but your app must be designed so any copy can handle any request.

    Two lessons from the simulator:

    1. Latency explodes before you hit 100%. At 50% utilization a request rarely waits. At 90%, it waits about ten times as long as at idle. Running servers "hot" to save money costs you tail latency. Most teams aim for 50–70% at normal peak.
    2. Vertical has a wall; horizontal has a bill. The X-Large instance handles 4x the load of a Small for almost 6x the price. Four Small instances match one X-Large for $0.80 an hour instead of $1.15, and losing one of them only costs a quarter of capacity instead of all of it.

    Analogy: identical cranes

    A port can add cranes along the quay only if any crane can unload any ship. If each crane operator kept their own private notebook of where they put boxes, a ship would have to wait for "its" crane. Stateless servers are interchangeable cranes: the notebook (state) lives in the shared yard system (database, cache), not in the operator's pocket.

    Stateless: the precondition for scaling out

    A service is stateless when it keeps nothing between requests that another instance would need. Any instance can serve any request, so the load balancer can send traffic anywhere, and instances can be added, removed, or crash without anyone noticing.

    Liveness versus readiness

    These two checks sound alike but trigger different actions, and mixing them up causes outages:

    • Liveness: "Is the process stuck?" A failing liveness check gets the instance restarted. Keep it trivial; never check the database here. If the database is down and liveness checks it, the orchestrator restarts every instance in a loop, making things worse.
    • Readiness: "Should I receive traffic right now?" A failing readiness check takes the instance out of the load balancer without killing it. Use it during startup (cache warm-up, migrations) and when a critical dependency is unreachable.

    Autoscaling

    Once your app is stateless, the platform can add and remove instances automatically based on a signal. Common choices:

    Reactive autoscaling always lags: new instances take time to start and warm up. If your peaks are predictable (BlueHarbor's Monday morning, peak shipping season), scale ahead of time on a schedule, and let reactive rules handle the surprises. On Azure Container Apps and Kubernetes, scaling rules based on queues and events are typically built on KEDA.

    In the real world: databases scale differently

    Everything above is about the app tier, which is the easy part. Databases hold state by definition, so you can't just add copies. The usual path is: scale up the database, add caching, add read replicas, then split data across databases (sharding). That's the heart of Part 2.

    Common pitfalls

    • Sticky sessions as a crutch. Pinning users to one instance hides state problems until that instance dies or deploys. Use it only as a deliberate optimization, never as the fix.
    • Scaling the app into the database. Going from 3 to 30 instances can multiply database connections and load 10x. The database becomes the bottleneck you just moved the problem to.
    • No graceful shutdown. When an instance is removed, in-flight requests should finish. ASP.NET Core honors a shutdown timeout; make sure your platform's drain period is longer than your slowest requests.
    • Untested capacity. Without a load test, "one instance handles 800 requests per second" is a guess. Measure it (k6, Azure Load Testing, NBomber).

    JuniorWhat's the difference between vertical and horizontal scaling? When would you use each?▶

    MidYou go from one to three instances of an ASP.NET Core app and users start getting logged out randomly. Why?▶

    Most likely Data Protection keys. ASP.NET Core encrypts auth cookies with keys that, by default, are stored per machine.     Likely follow-up: "Why not just enable sticky sessions?" It masks the problem: the user is logged out again whenever their instance restarts or is scaled in, and load spreads unevenly.
    MidWhy does latency rise sharply as a server approaches 100% utilization?▶

    Requests don't arrive evenly; they come in bursts. When a server is busy, new arrivals wait in a queue. In simple queueing models, waiting time grows roughly with 1 / (1 − utilization): at 50% utilization waits are about 2x the service time, at 90% about 10x, at 99% about 100x.

    That's why capacity planning targets 50–70% at normal peak, leaving headroom for bursts and for losing an instance.

    Likely follow-up: "What happens past 100%?" The queue grows without bound; requests time out, clients retry, adding more load. Without load shedding or rate limiting, this becomes a cascading failure.

    Building blocks

    2.1 Load balancing

    Spreading requests across servers so that no single one is overwhelmed, and routing around the ones that fail.

    About 25 minutesLevel: beginner to intermediate1 simulator

    In Part 1 you made the app stateless so you could run several copies. A load balancer is what makes those copies useful: it sits in front of them, receives every request, and decides which instance handles it. It does four jobs:

    • Distribute load so each instance does a fair share.
    • Detect failure with health checks and stop sending traffic to broken instances.
    • Enable zero-downtime deploys: drain one instance, update it, put it back.
    • Hide the topology: clients see one address no matter how many servers sit behind it.

    Analogy: the terminal gate dispatcher

    Trucks arrive at a container terminal's gate. A dispatcher assigns each truck to a loading lane. A naive dispatcher sends trucks to lanes in strict rotation. A smart one looks at which lanes have the shortest queues, and stops sending trucks to a lane whose crane just broke. That decision rule is the load balancing algorithm.

    The algorithms

    With server C slow, round robin keeps feeding it a quarter of all traffic even though it can only handle a twelfth, so its queue grows without limit and p95 latency climbs for everyone unlucky enough to land there.     Health checks: active and passive

    • Active: the balancer calls each server's health endpoint (your /health/ready from 1.5) every few seconds. After a few consecutive failures, the server is removed; after successes, it's added back.
    • Passive: the balancer watches real traffic. If requests to a server keep failing or timing out, it's taken out for a cooling-off period. Faster to react, needs no extra endpoint.

    Use both. Active checks catch a server that's broken but receiving no traffic; passive checks catch failures between active probes.

    Load balancers come in layers

    In .NET: YARP

    YARP (Yet Another Reverse Proxy) is a library that turns an ASP.NET Core app into a programmable L7 load balancer and API gateway. Because it's just ASP.NET Core, you can add authentication, rate limiting, and custom logic with the same middleware you already know.

    Built-in YARP policies include PowerOfTwoChoices (the default), RoundRobin, LeastRequests, Random, and FirstAlphabetical (for active/standby setups). You can write your own by implementing ILoadBalancingPolicy.

    In the real world: who balances the balancer?

    A single load balancer is a single point of failure. Managed cloud load balancers (Azure Load Balancer, Application Gateway, Front Door, AWS ALB/NLB) are internally redundant across machines and zones. If you run your own (YARP, NGINX, HAProxy), run at least two instances and put a managed L4 balancer or DNS in front of them. Most teams use a managed service at the edge and YARP only where they need custom logic.

    Common pitfalls

    • Deep health checks. If every instance's health check calls the database, a database blip marks all instances unhealthy at once, and the balancer has nowhere to send traffic. Keep checks shallow, or fail open when all instances fail.
    • Long-lived connections. WebSockets and gRPC streams stick to the server they connected to. New instances get no traffic until clients reconnect. Balance on new connections, and occasionally recycle long ones.
    • Retrying non-idempotent requests. A balancer that retries a timed-out POST /bookings on another server can create two bookings. Only retry safe methods, or use idempotency keys (Part 3).
    • Unbalanced zones. Three instances in zone 1 and one in zone 2 with zone-level balancing gives the lone instance half the traffic.

    JuniorWhat does a load balancer do, and what happens when one backend server goes down?▶

    It accepts client traffic on one address and spreads it across several backend servers using an algorithm such as round robin or least connections. It also health-checks the backends. When a server fails its health checks, the balancer stops routing to it; requests in flight to that server may fail, and clients or the balancer may retry them elsewhere. When the server recovers and passes checks again, it's added back.

    Likely follow-up: "How quickly is a dead server removed?" It depends on the check interval and failure threshold, for example 5 seconds × 3 failures = up to 15 seconds. Passive health checks on real traffic shorten that.
    MidWhy can round robin perform badly, and what would you use instead?▶

    Round robin assumes all servers are equally fast and all requests cost the same. When one server slows down (GC pause, noisy neighbor, a few expensive requests), round robin keeps sending it the same share, so its queue grows and tail latency spikes.

    Least requests sends to the server with the fewest in-flight requests, adapting automatically. With many balancer instances, power of two choices is often better: each balancer samples two servers and picks the less loaded one, which avoids all balancers piling onto the same server based on slightly stale counts.

    Likely follow-up: "Why does picking the best of only two random servers work so well?" Mathematically, sampling two choices exponentially reduces the maximum queue length compared to one random choice, while needing very little information.
    MidWhat's the difference between active and passive health checks? Why might a health check cause an outage?▶

    Active checks probe an endpoint on a schedule; passive checks infer health from real request failures. Active catches idle failures, passive reacts faster under traffic.

    The outage risk is a "deep" check that tests shared dependencies. If the database has a 10-second hiccup and every instance's check includes the database, every instance fails at once and the balancer removes them all, turning a brief degradation into a full outage. Keep readiness checks about the instance itself, or configure the balancer to keep routing when all backends look unhealthy (fail open).

    Likely follow-up: "So should a readiness check never check the database?" It can check that this instance can reach its dependencies at startup, but in steady state be careful about shared dependencies that would fail all instances together.
    SeniorDesign load balancing for an API served from two regions, with one region's data center failing.▶

    Three tiers. At the edge, a global anycast service (Azure Front Door or similar) routes users to the nearest healthy region using latency-based routing and its own health probes against each region's gateway. In each region, an L7 gateway routes by path to services and terminates TLS. Within each service, the platform spreads across instances in multiple availability zones.

    For a regional failure: edge probes fail, Front Door shifts all traffic to the healthy region within tens of seconds. That region must have capacity for 2x traffic, either pre-provisioned or with fast autoscaling, and its database must be able to accept writes (replicated, with a failover plan; see 2.4). Cached DNS is less of an issue because anycast keeps the same IP.

    Likely follow-up: "What about users mid-session when failover happens?" Stateless services and tokens (not server sessions) let them continue; in-flight requests fail and should be retried by idempotent clients.

    2.2 Caching

    Keeping copies of data where they're fast to reach, and the hard part: knowing when those copies are wrong.

    About 35 minutesLevel: intermediate1 visualizer

    A cache is a fast, usually smaller store holding copies of data that's expensive to get. From the latency ladder in 1.4: a Redis lookup takes about 1 ms, an in-process memory lookup takes microseconds, while a database query might take 5–50 ms and a partner API 200 ms. If most requests ask for the same popular data, serving them from a cache cuts latency and takes load off the database at the same time.

    Two numbers describe a cache:

    • Hit ratio: the fraction of lookups found in the cache. 95% means only 1 in 20 requests reaches the database.
    • Staleness: how out of date a cached copy can be. Every cache trades some freshness for speed.

    Where caches live

    A single request can pass through several caches. The closer to the user, the faster, and the harder to invalidate.

    Eviction: what to throw out when the cache is full

    Memory is limited, so caches evict entries. The policy decides which. Run the same access sequence through three policies side by side and compare hit counts. The cache here holds only 3 items, so you can see every decision.

    Eviction policy visualizer

    Interactive
    Sequence:

    • LRU (least recently used) evicts whatever hasn't been touched for longest. Great default; adapts quickly. Weakness: one big scan (a report reading every container once) flushes out genuinely hot data.
    • LFU (least frequently used) evicts whatever has been used least often. Protects hot items from scans. Weakness: items that were popular yesterday hang on too long.
    • FIFO evicts the oldest entry regardless of use. Simple and cheap, usually worse.
    • TTL (time to live) isn't really eviction but expiry: entries are removed after a fixed time. Used alongside the others to bound staleness.

    Redis offers allkeys-lru and allkeys-lfu (approximate versions) among its maxmemory-policy settings. For a pure cache, one of these is the right choice; the default on many installs is noeviction, which makes writes fail when memory is full.

    The hard part: invalidation

    When the data changes, cached copies become stale. Your options, from simplest to most precise:

    1. Expire by time (TTL). Accept up to N seconds of staleness. Simple and robust; pick N from the business requirement ("tracking may be 60 seconds stale").
    2. Delete on write. After updating the database, delete the cache key so the next read reloads it. Delete rather than overwrite: it's safer under concurrent writes.
    3. Tag-based invalidation. Group entries under tags (e.g., voyage:AE7-042) and invalidate all of them at once. HybridCache supports this.
    4. Versioned keys. Put a version in the key (schedule:v42:NLRTM); bump the version to make all old entries unreachable.
    5. Event-driven. Publish a "VoyageUpdated" event; every service holding related cache entries invalidates them (Part 3 messaging).

    The stale-set race

    Request A misses and reads the old value from the database. Meanwhile, request B updates the database and deletes the key. Then A, still holding the old value, writes it into the cache. The cache now holds stale data until the TTL expires. This is why you always keep a TTL even when you invalidate explicitly: it's the safety net that bounds how long any bug or race can leave data wrong.

    HybridCache (package Microsoft.Extensions.Caching.Hybrid, stable since .NET 9 and the recommended default for new .NET 10 projects) gives you a two-level cache behind one API: a local in-memory L1 per instance, plus an optional distributed L2 such as Redis. It also coalesces concurrent requests for the same key, so a stampede within one instance becomes a single database call.

    Two details worth noticing. First, the update writes to the database before invalidating; the reverse order opens a window where a reader reloads the old value. Second, the local L1 expiration is kept short. When another instance invalidates a key, your instance's L1 copy may survive until it expires, so L1 lifetime is effectively your staleness bound across instances.

    Choosing a Redis in 2026

    On Azure, new deployments should use Azure Managed Redis. Microsoft is retiring Azure Cache for Redis: the Enterprise tiers on March 31, 2027, and the Basic, Standard, and Premium tiers on September 30, 2028. On AWS and Google Cloud the managed default has shifted toward Valkey, the open-source Redis fork. Your .NET code (StackExchange.Redis) works with all of them; the differences are licensing, price, and features.

    Output caching: cache the whole HTTP response

    For endpoints whose response is identical for many users (the vessel arrival board from Part 1's exercise), ASP.NET Core's output caching stores the entire response and skips your endpoint entirely.

    Common pitfalls

    • Caching per-user data under a shared key. Shipper A sees shipper B's bookings. Always include the tenant or user in the key for user-specific data, and be careful with output caching on authenticated endpoints.
    • No TTL. Entries live forever, and any missed invalidation is permanent.
    • The cache as the only copy. A cache can be flushed at any time. If losing it loses data, it isn't a cache.
    • Treating a cold cache as impossible. After a deploy or a Redis failover, the hit ratio is zero. Can the database survive full traffic for a few minutes? If not, warm the cache or limit traffic.
    • Caching huge objects. Serializing a 5 MB list on every hit can cost more than the query it replaces.

    Interview questions

    JuniorExplain cache-aside. What happens on a hit, and on a miss?▶

    The application checks the cache first. On a hit, it returns the cached value without touching the database. On a miss, it reads from the database, stores the result in the cache with a TTL, and returns it. On writes, the app updates the database and then deletes the cache key so the next read reloads fresh data.

    Likely follow-up: "Why delete the key instead of updating it with the new value?" Two concurrent writers can update the cache in a different order from the database, leaving the older value in the cache. Deleting avoids that ordering problem.
    MidWhat is a cache stampede and how do you prevent it?▶

    When a popular key expires, many concurrent requests miss at the same moment and all hit the database to rebuild the same value. The database spikes, slows down, and more requests pile up.

    Fixes: coalesce requests so only one rebuilds while others wait (HybridCache does this per instance; a short Redis lock extends it across instances); add random jitter to TTLs so keys don't expire together; refresh popular keys before they expire; or serve the stale value while one request refreshes in the background.

    Likely follow-up: "HybridCache coalesces within one instance. You have 40 instances. Is that enough?" Worst case is 40 concurrent rebuilds instead of thousands, usually acceptable. If not, add a distributed lock or refresh-ahead.
    MidLRU versus LFU: when would each be the better choice?▶

    LRU suits workloads where recent use predicts future use and popularity changes over time, like tracking lookups for containers currently in transit. LFU suits workloads with a stable set of hot items that must survive occasional scans, like reference data (ports, vessel lists) mixed with bulk exports that touch everything once.

    Modern caches often blend both (e.g., W-TinyLFU), and Redis offers approximate LRU and LFU.

    Likely follow-up: "A nightly report reads every container once and the morning hit ratio crashes. What's happening?" Scan pollution under LRU. Fix with LFU, by bypassing the cache for batch jobs, or with a separate cache for them.
    SeniorYour service runs 30 instances with an in-memory cache. Users report seeing old vessel ETAs after updates. Diagnose and fix.▶

    Each instance has its own in-memory copy. The update path invalidates only the instance that handled the write, or none. The other 29 serve stale data until their entries expire, and if TTLs are long or missing, for a long time.

    Options, depending on how fresh it must be:

    • Short local TTLs as the staleness bound, plus Redis as the shared L2 (HybridCache pattern), invalidated on write.
    • Broadcast invalidations: publish an event (Redis pub/sub or a message bus) that every instance subscribes to and evicts the local key.
    • For data that must never be stale (capacity, prices at booking), don't cache it locally at all; read the source of truth.

    Then define the staleness requirement explicitly with product owners. "ETAs may be up to 60 seconds old" turns an endless argument into a TTL.

    Likely follow-up: "Pub/sub messages can be lost. Then what?" That's why the TTL stays as the backstop: a lost invalidation means stale data for at most one TTL.

    2.3 Databases, indexes, and transactions

    Choosing the right kind of database, making queries fast with indexes, and keeping data correct when many users write at once.

    About 40 minutesLevel: intermediate2 interactive tools

    The database is usually the heart of a system and the hardest part to change later. Three questions decide most database designs: what shape is the data, how will it be queried, and how correct must it be under concurrent writes.

    Relational (SQL) databases

    Relational databases (PostgreSQL, SQL Server, MySQL, Azure SQL) store data in tables with a fixed schema and relationships between them. Their superpower is transactions with ACID guarantees:

    • Atomicity: all statements in a transaction succeed, or none do. A booking and its invoice line are saved together or not at all.
    • Consistency: constraints (foreign keys, unique keys, checks) always hold after a transaction.
    • Isolation: concurrent transactions don't see each other's half-finished work (to a configurable degree, below).
    • Durability: once committed, data survives crashes; it's in the write-ahead log on disk.

    They also give you flexible querying: joins, aggregates, and ad-hoc questions you didn't plan for. Start with a relational database unless you have a specific reason not to.

    The NoSQL families

    "NoSQL" isn't one thing. It's several kinds of databases, each built around a particular access pattern, usually giving up joins or multi-row transactions in exchange for easier horizontal scaling or a better fit for that pattern.

    JuniorWhat does ACID stand for? Give an example of each from a booking system.▶

    MidA query filtering by occurred_at is slow even though there's an index on (container_id, occurred_at). Why?▶

    A composite B-tree index is sorted by its first column, then by the second within each first-column value. Without a filter on container_id, the database can't use the sorted order to find a time range; it would have to scan the whole index or the table. It's like searching a phone book sorted by last name for everyone named "Anna."

    Fix: add an index leading with occurred_at if that query matters, or for very large time-ordered tables, partition by time.

    Likely follow-up: "What's the cost of adding that index?" Slower inserts (every event now updates another B-tree), more storage, more memory pressure. Worth it only if the query is frequent or important.
    MidOptimistic versus pessimistic concurrency: how do they work and when do you choose each?▶

    Optimistic: read freely, and when saving, check that the row hasn't changed since you read it (via a version column). If it has, fail and retry. No locks are held while the user or code thinks. Pessimistic: lock the row when reading (SELECT … FOR UPDATE) so others wait until you commit.

    Choose optimistic when conflicts are rare (most edits to different bookings) and you don't want locks held across slow work. Choose pessimistic when conflicts are frequent on the same rows (a hot voyage in peak season), where optimistic retries would thrash. When the rule fits in one statement, an atomic conditional update beats both.

    Likely follow-up: "What's the danger with pessimistic locks?" Deadlocks when two transactions lock rows in different orders, and long waits if a transaction holds a lock during a slow operation like an HTTP call.
    SeniorExplain write skew with an example, and how you would prevent it.▶

    Write skew happens when two transactions each read a shared condition, both see it satisfied, and each writes to different rows, together breaking the rule. Example: a terminal rule says at least one crane operator must be on shift per berth. Two operators on the same berth each check "is someone else on shift?", both see yes, and both sign off. Neither updated the same row, so row-level version checks don't catch it, and snapshot isolation allows it.

    Prevention: run that transaction at Serializable isolation (and retry on serialization failures); or materialize the conflict by locking a shared row, such as SELECT … FOR UPDATE on the berth row, so the two transactions conflict on something concrete; or enforce the rule with a database constraint where possible.

    Likely follow-up: "Serializable in PostgreSQL can abort transactions. How do you handle that in .NET?" Catch the serialization failure (SQLSTATE 40001) and retry the whole transaction, for example through an EF Core execution strategy wrapped around the unit of work.

    2.4 Replication

    Keeping copies of the same data on several machines: for survival, for read capacity, and for distance. And the price you pay in lag.

    About 30 minutesLevel: intermediate2 interactive tools

    Replication means keeping the same data on multiple machines, called replicas. Three reasons to do it:

    • Availability and durability: if one machine dies, another has the data and can take over.
    • Read scaling: spread read queries across several copies.
    • Locality: put a copy near users in another region to cut read latency.

    Copying data that never changes is trivial. All the difficulty is in handling changes: who accepts writes, and how quickly the other copies find out.

    Leader-follower (primary-replica)

    The most common setup. One node, the leader (primary), accepts all writes. It streams its change log to followers (replicas, standbys), which apply the changes in the same order. Reads can go to any node. PostgreSQL streaming replication, SQL Server Always On availability groups, and MySQL replication all work this way.

    The key decision is when the leader confirms a write to the client:

    ModeLeader confirms after…Write latencyIf the leader dies right after confirming
    AsynchronousWriting to its own logLowestRecent confirmed writes can be lost
    SynchronousEvery follower has the changeHighest; one slow follower stalls all writesNo loss
    Semi-synchronous / quorumAt least one (or a majority of) followers have itMediumNo loss as long as that follower survives

    Most production setups use asynchronous replication to read replicas and synchronous (or quorum) replication to one standby in another availability zone for failover. Managed services like Azure Database for PostgreSQL with zone-redundant high availability do exactly this for you.

    Replication lag and "where's my booking?"

    With asynchronous followers, there's always a delay between a write on the leader and its appearance on followers: usually milliseconds, but seconds or minutes under heavy load or after a network hiccup. Try it: create a booking, then immediately reload the page, which reads from a replica.

    Replication lag

    Animated

    The anomaly you just saw breaks a guarantee called read-your-writes: a user should always see their own changes. Ways to provide it:

    • Read from the leader for things the user may have just changed (their own bookings), or for a short window after any write.
    • Track the log position of the user's last write; only read from replicas that have caught up to it.
    • Return the created object in the write response, so the UI doesn't need to re-read it immediately.

    A related anomaly: a user refreshes twice, hits two different replicas with different lag, and sees data go backwards in time. Monotonic reads prevent this, often by pinning each user's reads to the same replica.

    Routing reads to replicas in .NET

    Failover: when the leader dies

    A follower must be promoted to leader, and clients must start sending writes to it. That sounds simple; it hides three classic problems:

    1. Lost writes: with async replication, the new leader may be missing the old leader's last few writes.
    2. Split brain: the old leader wasn't dead, just unreachable. Now two nodes accept writes, and data diverges. Systems prevent this with fencing: the old leader is forcibly cut off, or every write carries a leadership term number that storage rejects if it's outdated.
    3. False alarms: a timeout too short causes failovers during brief network blips, each one disruptive. Too long, and a real failure means minutes of downtime.

    This is why most teams use managed databases with automatic failover rather than building it themselves. Your job is to make the application survive it: reconnect, retry idempotent operations, and keep connection timeouts sane.

    Multi-leader and leaderless replication

    Multi-leader: several nodes accept writes, typically one per region, and replicate to each other. Writes are fast everywhere, but two regions can modify the same record concurrently, creating conflicts. Resolution strategies include last-writer-wins (simple, silently drops one write), merging (CRDTs, data types designed to merge), or application-specific rules. Cosmos DB multi-region writes is an example.

    Leaderless (Dynamo-style: Cassandra, ScyllaDB): the client writes to several replicas directly and reads from several. With N replicas, a write waits for W acknowledgements and a read queries R replicas. If W + R > N, every read overlaps with at least one replica that has the latest write.

    • Replicas aren't backups. A DELETE without a WHERE replicates to every follower in milliseconds. You still need point-in-time backups.
    • Assuming lag is always tiny. It's tiny until a big migration or batch job runs, then it's minutes. Monitor lag and alert on it.

    JuniorWhy replicate a database? Name two benefits and one cost.▶

    Benefits: high availability (a replica takes over if the primary fails), read scaling (spread reads), and lower latency for distant users. Costs: replication lag means replicas can be stale; more machines to pay for and operate; and failover complexity.

    MidA user updates their notification settings and the page reloads showing the old settings. What happened and how do you fix it?▶

    The write went to the primary, but the reload was served by a read replica that hadn't yet received the change: replication lag breaking read-your-writes.

    Fixes: route reads of the user's own data to the primary (at least for a short window after they write); track the write's log position (LSN) and only use replicas that have reached it; or return the updated settings in the write response so the client doesn't re-read.

    Likely follow-up: "Doesn't routing to the primary defeat the point of replicas?" Only for a small fraction of reads: users' own recently-changed data. Public, high-volume reads still go to replicas.
    MidWith N = 5 replicas, choose W and R for strong reads, and explain the trade-off of your choice.▶

    Any W + R > 5 guarantees overlap. W = 3, R = 3 is balanced: both reads and writes tolerate 2 failed replicas. W = 5, R = 1 makes reads fast but any single failure blocks writes. W = 1, R = 5 is the reverse. Choose based on whether reads or writes are more frequent and which you'd rather keep available during failures.

    Likely follow-up: "Does W + R > N give you linearizability?" Not strictly; with concurrent writes, sloppy quorums, and clock-based conflict resolution there are edge cases. It gives a strong practical guarantee that reads see recent writes, not a full proof of linearizability.
    SeniorWhat is split brain, and how do real systems prevent it during failover?▶

    Split brain is two nodes both believing they're the leader and both accepting writes, typically because the old leader was partitioned rather than dead. Data diverges and is painful to reconcile.

    Prevention combines: consensus on leadership (a majority of nodes, e.g., via Raft or etcd, must agree on the new leader, so a minority-side node can't keep leading); leases (leadership expires unless renewed, and the old leader stops accepting writes when it can't renew); and fencing tokens (a monotonically increasing term number attached to writes, so storage rejects writes from an outdated leader). Some systems also STONITH: forcibly power off the old node.

    Likely follow-up: "Why does a two-node cluster struggle here?" Neither side can form a majority alone, so you need a third voter (a witness or quorum node) to break ties.

    2.5 Partitioning and sharding

    When one database can't hold all the data or absorb all the writes: splitting it into pieces, and choosing how.

    About 35 minutesLevel: intermediate to advanced1 interactive ring

    Replication copies the same data to several machines, which helps reads and availability. It doesn't help when there's too much data for one machine, or too many writes for one leader. For that you split the data itself: each piece, called a partition or shard, holds a subset of the rows and lives on a different node. Each shard is usually also replicated, so the two techniques work together.

    Terms you'll hear: partitioning is the general idea, and it can happen inside one database (PostgreSQL table partitioning by month). Sharding usually means partitions spread across separate database servers.

    Hot partitions

    Even a well-chosen key can be skewed. If one container (or one celebrity user, one viral product) gets a huge share of traffic, its shard melts while others idle. Fixes: cache the hot key heavily; split it by appending a suffix (key#0 … key#9) and spread writes across the variants, reading all ten when needed; or isolate known giants (a carrier with 40% of volume gets dedicated shards).

    The resharding problem, and consistent hashing

    The obvious hash scheme is shard = hash(key) % N. It spreads data nicely, until you add a fifth shard to four. Now % 5 gives a different answer for about 80% of keys, and nearly all your data has to move at once.

    Consistent hashing fixes this. Picture a ring of hash values. Each node is placed at a point on the ring (by hashing its name), and each key belongs to the first node clockwise from the key's own position. Adding a node only takes over the keys between it and its neighbor; everything else stays put. Try it:

    Two things to notice. First, with plain nodes, the share each node gets is uneven, because node positions are random. Second, turning on virtual nodes fixes that: each physical node is placed at many points on the ring, which evens out the shares and, when a node leaves, spreads its keys across all remaining nodes instead of dumping them on one neighbor. Cassandra, DynamoDB, and many caches use this idea.

    What sharding costs you

    • Cross-shard queries: "all delayed containers for customer X" may need to ask every shard and merge the results (scatter-gather). Slow, and as slow as the slowest shard.
    • Cross-shard transactions: an atomic change spanning two shards needs distributed transactions or sagas (Part 4).
    • Secondary indexes: an index on anything other than the partition key is either local (each shard indexes its own rows, so queries fan out) or global (a separately partitioned index, updated asynchronously).
    • Operations: backups, schema migrations, and monitoring now happen N times.

    In the real world: let the database shard for you

    Hand-rolled sharding in application code is rarely the best first move. Azure Cosmos DB partitions automatically by the partition key you choose; Citus (available as Azure Cosmos DB for PostgreSQL) distributes PostgreSQL tables across nodes; Cassandra and DynamoDB are built around it. Your most important job doesn't change: pick the partition key carefully, because changing it later usually means migrating all the data.

    Common pitfalls

    • Sharding too early. A single well-indexed PostgreSQL or SQL Server instance on good hardware handles terabytes and thousands of writes per second. Exhaust indexing, caching, replicas, and vertical scaling first.
    • Monotonic keys with range sharding. Sequential IDs or timestamps send every new write to the last shard.
    • Unbounded partitions. A partition per carrier keeps growing forever. Add a time component or enforce size limits.

    Interview questions

    JuniorWhat's the difference between replication and sharding?▶

    Replication stores the same data on multiple nodes: it improves availability and read capacity. Sharding stores different subsets of the data on different nodes: it increases total storage and write capacity. Production systems usually do both: each shard is replicated.

    Likely follow-up: "Which one do you reach for first?" Replication, because it's simpler and fixes availability. Sharding when a single leader can't hold the data or absorb the writes.
    MidWhy is hash(key) % N a problem, and how does consistent hashing help?▶

    Changing N changes the result for most keys: going from 4 to 5 shards remaps about 80% of keys, forcing a massive data migration and cache wipe. Consistent hashing places nodes and keys on a ring; each key belongs to the next node clockwise. Adding or removing a node only moves the keys in the affected arc, roughly 1/N of the data. Virtual nodes (many ring positions per physical node) even out load and spread the moved keys across all nodes.

    Likely follow-up: "Why not just pre-create many more partitions than nodes?" That's a valid alternative (e.g., 1,024 fixed partitions assigned to nodes, moving whole partitions when scaling). Many systems do exactly that; it makes rebalancing a matter of reassigning partitions.
    MidChoose a partition key for booking data, where most queries are "bookings for customer X" and "bookings on voyage Y."▶

    Look at which query is more frequent and latency-critical. Customer portals query by customer constantly; voyage queries are operational, less frequent, and can tolerate more latency. Partition by customer, then serve voyage queries from a secondary index or, better, from a separate read model partitioned by voyage, updated by events (CQRS, Part 4).

    Check for skew: a few freight forwarders may have huge volumes. If so, use a compound key like (customer, month) or give big customers dedicated partitions.

    Likely follow-up: "How do you keep the voyage read model consistent?" Eventually consistent via events or change data capture; acceptable for operational views, not for capacity enforcement, which stays on the authoritative voyage record.

    First, determine whether it's data skew (that shard holds more data) or access skew (a few keys get disproportionate traffic). Per-key metrics or sampled query logs show hot keys quickly.

    • Hot key: cache it at L1 in the app tier, split writes across suffixed sub-keys, or rate limit the abusive client.
    • Data skew from a poor key: split that shard's range (range sharding) or move virtual nodes or partitions off it (hash sharding with fixed partitions).
    • Systematic skew (key choice is wrong): plan a migration to a better key, typically by dual-writing to a new layout, backfilling, verifying, and switching reads.
    Likely follow-up: "How do you move data between shards without downtime?" Copy in the background, keep it in sync with change data capture or dual writes, switch routing atomically for that partition, then clean up. Throttle the copy so it doesn't hurt live traffic.

    2.6 CAP, PACELC, and consistency models

    What a distributed database can and cannot promise when the network fails, and the spectrum of "consistent" in between.

    About 30 minutesLevel: intermediate to advanced1 simulator

    Once data lives on more than one machine (2.4 and 2.5), you have to decide what happens when those machines can't talk to each other. The CAP theorem is the famous framing, and it's widely misquoted.

    CAP, stated correctly

    The three properties:

    • Consistency (C): every read returns the most recent write, as if there were only one copy (linearizability).
    • Availability (A): every request to a working node gets a non-error response.
    • Partition tolerance (P): the system keeps operating when messages between nodes are lost or delayed.

    The common version, "pick any two of three," is misleading. Networks will partition; you don't get to opt out of P. The real statement is: when a network partition happens, a system must choose between consistency and availability. When there's no partition, you can have both.

    Partitions are rare. Most of the time, the real trade-off is between latency and consistency: waiting for replicas in other zones or regions to confirm makes every write slower. PACELC captures both: if Partitioned, choose A or C; Else, choose Latency or Consistency.

    Don't pick one consistency level for the whole system. Pick it per operation, based on what a wrong answer costs. Strong where money or capacity is at stake; session where users edit their own data; eventual where freshness barely matters and scale does.

    JuniorWhat does the CAP theorem say?▶

    A distributed data store can't guarantee both consistency (every read sees the latest write) and availability (every request gets a non-error response) when there's a network partition between its nodes.     MidWhat does PACELC add to CAP?▶

    CAP only talks about behavior during partitions, which are rare.     SeniorIn an AP system, two regions update the same shipment's status during a partition. How do you resolve the conflict when it heals?▶

    • Last-writer-wins by timestamp: simple, but clock skew can pick the wrong winner, and one update is silently lost.

    • Keep both and merge: store the events rather than the status (an append-only event log merges trivially, then the status is derived), or use CRDTs for counters and sets.
    • Surface to a human for rare, high-value conflicts.

    The strongest design avoids the conflict: model shipments as immutable events, which can be merged from any region, and compute the current state from them.

    Likely follow-up: "Why are clocks a problem for last-writer-wins?" Server clocks drift by milliseconds or more; a write that happened later can carry an earlier timestamp. Logical clocks (Lamport, vector clocks) or hybrid logical clocks address ordering more reliably.

    2.7 Blob storage and CDNs

    Where files live (bills of lading, photos, exports), and how static content reaches users around the world quickly.

    About 25 minutesLevel: beginner to intermediate

    Not all data belongs in a database. PDFs, images, video, and large exports are better stored in object storage (blob storage): Azure Blob Storage, Amazon S3, Google Cloud Storage. Objects are written once and read many times, addressed by a key (a path-like name), and stored with very high durability at a low price per gigabyte.

    Database rowObject storage
    Good forSmall, structured, frequently queried dataLarge, unstructured files
    UpdatesChange individual fieldsReplace the whole object
    QueriesRich (SQL, indexes)Get by key, list by prefix
    Cost per GBHigh (fast disks, replicas, compute)Very low, with cheaper tiers for cold data
    Serve directly to usersNo, through your APIYes, via signed URLs or a CDN

    The standard pattern: store the file in object storage, and store its metadata and key in the database. The booking row holds bl_document_key = "bookings/BK-88412/bl-v3.pdf", not the PDF bytes.

    Storage tiers and lifecycle

    Object stores offer tiers trading access cost for storage cost. Azure's are Hot, Cool, Cold, and Archive; Archive is very cheap to store but takes hours to read back. Lifecycle rules move objects automatically: BlueHarbor keeps bills of lading Hot for 90 days, Cool for 2 years, then Archive until the 7-year retention ends, then deletes them. This is how the 23 TB from 1.4 becomes affordable.

    Durability comes from redundancy options: copies within one data center, across availability zones, or across regions (geo-redundant). Choose based on how bad losing the data would be and whether you need to read it during a regional outage.

    Uploads: don't stream files through your API

    If every 10 MB upload flows through your ASP.NET Core instances, they spend memory, bandwidth, and threads just shuffling bytes. Instead, the API hands the client a short-lived, narrowly scoped signed URL (a SAS URL on Azure, a presigned URL on S3), and the client uploads directly to storage.

    CDNs: content close to users

    A content delivery network is a global fleet of edge servers that cache your content near users. A request from Singapore is answered by a Singapore edge instead of crossing to Europe. As you saw in 1.3, the edge also terminates TCP and TLS close to the user, which helps even for content that can't be cached.

    • Pull CDN: the edge fetches from your origin on the first miss and caches it. Easy; the default.
    • Push CDN: you upload content to the CDN ahead of time. Useful for large files you know will be popular (a new app release).

    What the edge caches, and for how long, is controlled by HTTP headers from your origin:

    ContentHeaderWhy
    Fingerprinted assets (app.3f9a1c.js)Cache-Control: public, max-age=31536000, immutableThe file name changes when content changes, so cache forever
    Public API data (arrival board)Cache-Control: public, max-age=60Matches the acceptable staleness
    Per-user dataCache-Control: private, no-storeMust never be cached at a shared edge

    To update cached content you can purge it from the CDN (slow to propagate, sometimes rate-limited) or, better, version the URL so new content has a new address. In ASP.NET Core, app.MapStaticAssets() (.NET 9+) fingerprints files at build time, serves compressed versions, and sets these caching headers for you.

    Common pitfalls

    • Public containers. Making a storage container publicly listable to "simplify downloads" has caused many real data leaks. Keep containers private and hand out signed URLs.
    • Long-lived or broad signed URLs. A SAS valid for a year with write access to a whole container is effectively a password in a link. Scope to one blob, minimal permissions, minutes of validity.
    • Caching authenticated responses at the CDN. One missing private header can serve one customer's data to another.
    • Trusting uploads. Validate file type and size after upload, and scan for malware before anyone else downloads the file.

    3.2 Idempotency, retries, and backoff

    Networks fail mid-request. How to retry safely without double bookings, and without your retries taking the system down.

    About 25 minutesLevel: intermediate1 simulator

    A partner's system sends POST /bookings. The connection drops before the response arrives. Did the booking get created? The client can't know. There are three possibilities: the request never arrived, it arrived and failed, or it succeeded and only the response was lost. If the client retries and it was the third case, you now have two bookings. This is the most common source of duplicate orders, payments, and shipments in distributed systems.

    Idempotency keys

    The fix is to make the operation idempotent. The client generates a unique key per logical operation and sends it with every attempt (Idempotency-Key: 5f2b…). The server remembers the key and the result. A repeated key returns the stored result instead of doing the work again.

    The details that make it correct:

    • Store the key in the same transaction as the work, with a unique constraint. Otherwise a crash between "do the work" and "remember the key" reopens the gap.
    • Handle concurrent duplicates. If two attempts arrive at once, the unique constraint lets one win; the other should get 409 Conflict ("still processing, retry shortly") or wait.
    • Check the request matches. Same key with a different body is a client bug: reject it with 422.
    • Expire keys after a sensible window (24 hours to a few days).

    Retrying well: backoff and jitter

    Retries fix transient failures (a dropped connection, a brief overload, a failover). Retries done badly cause outages. If a service hiccups and 1,000 clients all retry after exactly 1 second, the service gets hit by 1,000 requests at once, fails again, and they all retry again at the same moment. This is a retry storm, and it can keep a recovering service down indefinitely.

    Two techniques prevent it:

    • Exponential backoff: wait longer after each failure (e.g., 0.2 s, 0.4 s, 0.8 s, 1.6 s…), giving the service room to recover.
    • Jitter: randomize each wait, so clients spread out instead of retrying in lockstep.

    Retry storm simulator

    Interactive

    500 clients fail at the same instant because of a brief outage. The service can handle 120 requests per 250 ms slot; anything above that fails and is retried again (up to 6 attempts).

    With fixed or plain exponential delays, every client retries in the same slot and the spikes keep exceeding capacity. With jitter, the retries smear out under the capacity line and almost everyone succeeds quickly. Rules for production retries:

    1. Only retry transient errors (timeouts, 503, 429, connection resets), never 400 or 422.
    2. Only retry idempotent operations, or ones protected by idempotency keys.
    3. Use backoff with jitter and a cap on both attempts and total time.
    4. Honor Retry-After headers from the server.
    5. Retry at one layer only. If the browser, the gateway, and the service each retry 3 times, one failure becomes 27 calls downstream.

    In the real world

    Payment providers popularized idempotency keys for exactly this reason: a duplicate charge is unacceptable, and network failures are guaranteed. The same applies to logistics: a duplicated booking reserves capacity twice; a duplicated "gate out" event can trigger a second customs filing. Any API that creates things or moves money should accept idempotency keys.

    Interview questions

    JuniorA client times out on POST /bookings. Why is retrying risky, and how do you make it safe?▶

    A timeout doesn't tell the client whether the server processed the request. If it did and only the response was lost, a retry creates a second booking. Make it safe with an idempotency key: the client sends the same unique key on every attempt; the server stores the key with the result in the same transaction and returns the stored result for repeats.

    Likely follow-up: "Who generates the key?" The client, once per logical operation (e.g., when the user clicks "Book"), and reuses it for all retries of that operation.
    MidWhy add jitter to exponential backoff?▶

    Without jitter, clients that failed together retry together: backoff increases the gap between waves but each wave is still a synchronized spike that can exceed capacity again. Jitter randomizes each client's delay, spreading retries over time so load stays below capacity and the service can recover.

    Likely follow-up: "What's 'full jitter'?" Choose the delay uniformly between 0 and the exponential backoff value. It spreads load the most and tends to perform best in contention.
    SeniorDesign idempotency for a booking endpoint that also publishes a "BookingCreated" event to a message broker.▶

A retried request finds the existing key and returns the stored response, so no second booking and no second outbox row are created.

    The relay may still publish an event twice (if it crashes after publishing but before marking the row sent), so consumers must also be idempotent, deduplicating by event ID.

    Likely follow-up: "Why not publish then commit, or commit then publish?" Publish-then-commit can announce a booking that rolls back; commit-then-publish can lose the event if the process crashes between the two. The outbox removes the gap.

    Server-sent events in .NET 10

    For one-way updates to browsers, SSE is now the simplest option. .NET 10 added native support: return TypedResults.ServerSentEvents from any IAsyncEnumerable, and the browser's built-in EventSource handles reconnection.

    SignalR and scaling persistent connections

    SignalR is ASP.NET Core's real-time framework. It picks the best transport automatically (WebSockets, then SSE, then long polling), adds groups ("everyone watching voyage AE7-042"), reconnection, and typed hubs. The scaling problem it solves is the same one the comment above mentions: when a message is produced on instance A, but the user's connection lives on instance B, something must route it across instances. Options:

    • Redis backplane: every instance publishes through Redis pub/sub, every instance receives and delivers to its local connections.
    • Azure SignalR Service: a managed service holds all client connections; your app instances just send messages to it. Offloads tens of thousands of connections from your servers.

    Persistent connections change capacity planning: each connected user holds memory and a socket even when idle, and load balancers must support long-lived connections and WebSocket upgrades. Plan in "concurrent connections per instance," not just requests per second.

    Webhooks: push to other servers

    Freight forwarders don't keep browsers open; their systems want BlueHarbor to call them. A webhook is an HTTP POST from you to a URL they registered, when an event happens. That's the push alternative to the 50,000 polls per second from Part 2's exercise. Production-grade webhooks need:

    • Signatures: sign each payload with an HMAC using a per-subscriber secret, and include a timestamp, so receivers can verify it's really from you and not replayed.
    • Retries with backoff: receivers will be down sometimes. Retry for hours with exponential backoff, then mark the subscription unhealthy.
    • Asynchronous delivery: never call partners inside your request path. Put deliveries on a queue (3.4) processed by workers, so one slow partner can't slow everyone.
    • At-least-once semantics, documented: include an event ID so receivers can deduplicate.
    • A replay API: "give me events since X" lets partners recover from long outages.

    Common pitfalls

    • Ignoring missed messages on reconnect. A phone loses signal for 30 seconds. Use event IDs (SSE's Last-Event-ID) or a "since" query so clients can catch up.
    • Unbounded per-connection buffers. One slow client can make the server buffer messages forever. Bound and drop, as the channel above does.
    • Treating webhooks as reliable. They're at-least-once at best; receivers will see duplicates and occasional reordering.
    • SSRF via webhook URLs. A subscriber registers http://169.254.169.254/… to make your server call internal endpoints. Validate and restrict destination addresses.

    SSE is one-way (server to client) over a normal HTTP response that stays open; it's text-based, works through most proxies, and browsers reconnect automatically and resume from the last event ID. For notifications and dashboards, SSE is simpler; for interactive two-way traffic, WebSockets.

    Likely follow-up: "Where does SignalR fit?" It's an abstraction over both (plus long polling), adding groups, reconnection, and scale-out via a backplane or Azure SignalR Service.
    MidYou run 6 instances of a SignalR app. A user isn't receiving updates sent from a background job. Why?▶

    The job ran on an instance that doesn't hold that user's connection. Each instance only knows its own connections, so the message was delivered nowhere.     Likely follow-up: "What do sticky sessions have to do with SignalR?" With some transports (long polling, SSE negotiation), the requests of one logical connection must reach the same server, so sticky sessions are required unless you use Azure SignalR Service or WebSockets only.
    SeniorDesign a webhook delivery system for 5,000 partner subscriptions and 2 million events a day.▶

    Events land in a durable stream. A matcher fans each event out into per-subscription delivery tasks on a queue. Workers deliver with HMAC signatures and timeouts, retry with exponential backoff and jitter over ~24 hours, and dead-letter after that. Isolate partners: per-subscriber concurrency limits and circuit breakers so one slow endpoint can't consume all workers (a bulkhead). Track health per subscription; auto-pause endpoints failing for a long time and notify the partner. Offer a replay API and include event IDs so partners can deduplicate and recover. Validate destination URLs to prevent SSRF.

    Rough numbers: 2 million events a day is ~23/s average; if each fans out to ~3 subscriptions, ~70 deliveries/s, which is modest, but a single partner outage can accumulate a large backlog, so storage and retry scheduling matter more than throughput.

    Likely follow-up: "Do partners need ordering?" Usually per container. Deliver sequentially per (subscription, container) key, or include sequence numbers so receivers can reorder.

    3.4 Messaging: queues, pub/sub, and streams

    Decoupling services in time: absorbing bursts, surviving downtime, and the truth about "exactly once."

    About 45 minutesLevel: intermediate to advanced1 simulator

    So far, services have talked synchronously: the caller waits for an answer. That couples them tightly. If the receiver is slow, the caller is slow; if it's down, the caller fails. Asynchronous messaging puts a broker in between. The sender drops a message and moves on; the receiver processes it when it can.

    • Temporal decoupling: the receiver can be down for an hour; messages wait.
    • Load leveling: a burst of 5,000 terminal events per second is absorbed by the queue and processed at a steady rate.
    • Fan-out: one "ContainerDischarged" event can trigger notifications, billing, and analytics without the producer knowing about any of them.

    Analogy: the container yard

    Ships unload in bursts; trucks collect boxes steadily throughout the day. The yard between them is a buffer: the ship doesn't wait for trucks, and trucks don't wait for ships. A message queue is the yard between a bursty producer and a steady consumer.

    Streams and partitions

    Kafka-style logs scale by splitting a topic into partitions. Messages with the same key (e.g., container number) always go to the same partition, so their order is preserved.     Dead-letter queues and poison messages

    A poison message fails every time: malformed JSON, a container number in the wrong format, a bug triggered by unusual data. Retrying forever wastes capacity and can block ordered processing. After N attempts, move it to a dead-letter queue (DLQ), alert someone, and let the rest flow. Treat the DLQ as an inbox that people must actually work: inspect, fix, and replay.

    Common pitfalls

    • Assuming ordering. Competing consumers process messages in parallel; "loaded" can be handled after "discharged." Use sessions or partition keys for per-entity order, and make handlers tolerate out-of-order events.
    • Huge messages. Brokers limit size (often 256 KB–1 MB). Store the payload in blob storage and send a reference ("claim check" pattern).
    • No monitoring of queue depth and age. A silently growing queue is an outage in slow motion. Alert on the age of the oldest message.
    • Publishing inside a database transaction. If the transaction rolls back, the message is already out. Use the outbox pattern (Part 4).

    JuniorWhat's the difference between a queue and a pub/sub topic?▶

    A queue delivers each message to one consumer among several competing ones: it distributes work.     MidIs exactly-once delivery possible? What do you do instead?▶

    Not end to end across independent systems: a consumer can always crash after doing its side effect but before acknowledging, causing redelivery.     Likely follow-up: "How long do you keep processed IDs?" Longer than the broker's maximum redelivery window, typically days, with cleanup.
    MidA Kafka topic has 6 partitions and your consumer group has 10 instances. What happens? How do you scale further?▶

    Likely follow-up: "Why not create 1,000 partitions from day one?" Each partition has overhead (files, replication, leader elections, rebalance time). Size for expected peak with headroom.

    Likely follow-up: "A terminal resends its whole day of events after an outage." Idempotency by event ID makes it harmless; the stream absorbs the volume; lag spikes and recovers.

    3.5 Rate limiting and backpressure

    Protecting a service from more traffic than it can handle, and being fair about who gets served.

    About 30 minutesLevel: intermediate1 simulator

    Every service has a limit. Without protection, one misbehaving partner script, one buggy client stuck in a retry loop, or one scraper can consume all capacity and take the service down for everyone. Rate limiting caps how many requests a client may make in a period; requests over the limit are rejected quickly with 429 Too Many Requests and a Retry-After header, which is far cheaper than letting them in.

    Rate limits serve three goals: protection (keep the service alive), fairness (one tenant can't starve others), and cost control or monetization (API tiers: 100 lookups/minute free, 10,000 for paid plans).

    Backpressure and load shedding

    Rate limiting protects you from clients. Backpressure protects components from each other: when a downstream part is saturated, it signals upstream to slow down instead of silently buffering until memory runs out. Bounded channels, bounded queues, connection pool limits, and 429/503 responses are all forms of backpressure. Load shedding is the last line: when overloaded, deliberately reject low-priority work (bulk exports, analytics) to keep critical paths (bookings, tracking) alive.

    Common pitfalls

    • Limiting by IP only. Many partners sit behind one corporate NAT, and attackers rotate IPs. Prefer authenticated identities (API keys, tenants), with IP as a fallback for anonymous traffic.
    • No Retry-After header. Clients guess, often badly, and retry immediately.
    • Rate limiting after the expensive work. The limiter must run before authentication-heavy or database-heavy middleware where possible.
    • Unbounded queues anywhere. Every queue needs a maximum; unbounded buffers just move the failure later and make it worse.

    4.1 Monolith, modular monolith, microservices

    Where to draw the boundaries in a system, and why the answer is usually "fewer services than you think."

    About 30 minutesLevel: intermediate

    Every system is split into parts somehow. The question is where the boundaries are, and whether they're boundaries in code (projects, namespaces, modules inside one deployable) or boundaries over the network (separate services). That choice decides how teams work, how failures spread, and how hard every change is.

    The case for starting with a modular monolith

    Microservices solve organizational scaling problems: many teams stepping on each other in one codebase, conflicting release schedules, parts with wildly different scaling needs. They introduce technical problems in exchange: network failures, distributed transactions, versioned contracts, and debugging across processes. For a small team, that's a bad trade.

    A modular monolith gets most of the design benefits: clear boundaries, ownership, and independent evolution of modules, with none of the network costs. Each module has a public API (an interface or a set of commands and queries), its own database schema, and no direct access to other modules' tables. If a module later needs to become a service, the boundary is already clean, so extraction is a mechanical change rather than a rewrite.

    Finding the boundaries

    Bad boundaries are worse than no boundaries: two services that must change together and call each other constantly are a distributed monolith, with all the costs of both. Good boundaries come from the business, not the technology:

    • Bounded contexts (from Domain-Driven Design): areas where a word has one precise meaning. "Container" in Equipment means a physical box with maintenance history; in Booking it means a slot of capacity of some size; in Tracking it's an ID with an event timeline. Three contexts, three models, three candidate modules.
    • High cohesion, low coupling: things that change together belong together. If every booking feature touches pricing, maybe pricing belongs inside Booking.
    • Data ownership: each piece of data has exactly one owner that writes it. Others get it through the owner's API or events.
    • Conway's law: systems mirror the communication structure of the organization that builds them. Align service boundaries with team boundaries, or the boundaries will erode.

    When microservices are worth it

    Split a module out when there's a concrete reason, such as: it needs to scale very differently (reefer telemetry ingestion versus the booking UI), it needs a different technology or runtime, it has a different reliability requirement and must be isolated, or a separate team needs to release it independently and often. Use the strangler fig pattern: route a slice of traffic to the new service behind a gateway (YARP from 2.1 is perfect for this), migrate piece by piece, and retire the old code when nothing calls it.

    Common pitfalls

    • Shared database between services. Two services writing the same tables are coupled through the schema; neither can change it alone. Each service owns its data.
    • Synchronous call chains. Service A calls B calls C calls D. Latency adds up, availability multiplies down (Part 1), and one slow service stalls all of them. Prefer events and local copies of the data you need.
    • Splitting by technical layer. A "database service," a "validation service," and an "API service" means every feature touches all three. Split by business capability.
    • Too many, too small. 40 services for a 6-person team means each person operates 7 services. Size services for teams, not for classes.

    Likely follow-up: "So when would you start with microservices?" Rarely: only with several teams and well-understood domain boundaries from day one. Otherwise, a modular monolith first.
    MidWhat is a distributed monolith, and how do you recognize one?▶

    A system split into services that can't actually change or deploy independently.     4.2 Sagas and the transactional outbox

    Keeping data consistent across services when a single ACID transaction isn't available.

    About 40 minutesLevel: advanced2 interactive demos

    Confirming a booking at BlueHarbor touches three services, each with its own database: Voyages reserves vessel capacity, Equipment allocates empty containers at the origin depot, and Payments charges a deposit. In a monolith, that's one transaction. Across services, there is no shared transaction. If Payments fails after Voyages reserved capacity, someone has to undo the reservation.

    Why not a distributed transaction (2PC)?

    Two-phase commit coordinates several databases: a coordinator asks every participant to "prepare" (lock and promise), then tells all to commit. It gives atomicity, but every participant holds locks while waiting for the slowest one, a coordinator crash at the wrong moment leaves participants blocked, and most modern brokers and cloud databases don't support it across services. It couples everyone's availability together. In practice, services use sagas instead.

    Sagas: a sequence of local transactions with compensations

    A saga breaks the operation into steps. Each step is a local transaction in one service. If a step fails, the saga runs compensating actions for the steps that already succeeded, in reverse order. Compensations are semantic undos ("release the capacity," "refund the deposit"), not database rollbacks: the reservation did exist for a few seconds, and other people may have seen it.

    • Forgetting timeouts. A saga waiting forever for a reply that was lost. Every waiting step needs a deadline and a decision on expiry.
    • Unbounded outbox tables. Delete or archive sent rows, or the relay's query slows down over time.
    • Assuming message order across aggregates. The outbox preserves order per service; consumers should still tolerate reordering between different entities.

    4.3 Event-driven design, CQRS, and event sourcing

    Three related ideas that are often confused: reacting to events, separating reads from writes, and storing history instead of state.

    1. Event-driven architecture

    2. CQRS: separate models for reading and writing

    Command Query Responsibility Segregation means the model you write through is different from the models you read from. The write side enforces rules on a normalized model (a voyage's capacity, a booking's lifecycle). The read side has read models (projections): denormalized views shaped exactly for each screen or query, updated from the write side's changes.

    Benefits: each side scales and evolves independently; read models are fast because they're precomputed; complex screens become simple lookups. Costs: read models are eventually consistent (usually milliseconds to seconds behind), and there's more infrastructure. Use CQRS where read and write needs genuinely differ, not as a default for every module. A lightweight version (separate query classes and DTOs over the same database) is useful almost everywhere.

    Normally a database stores current state: a row saying the container is "Discharged at Singapore." Event sourcing stores the sequence of events instead, in an append-only event store, and computes the current state by replaying them. Nothing is ever updated or deleted; corrections are new events.

      4.4 Resilience patterns

      Timeouts, circuit breakers, bulkheads, fallbacks, and hedging: stopping one sick dependency from taking everything down with it.

      About 35 minutesLevel: advanced1 simulator

      In a distributed system, something is always failing a little. The danger isn't one failure; it's cascading failure: a slow dependency makes callers wait, waiting requests pile up and hold threads and connections (Little's Law from 1.4), the callers become slow, their callers pile up, and within minutes a problem in one partner's ETA service has taken down the whole booking site. Resilience patterns break that chain.

      The circuit breaker

      Like an electrical breaker, it trips to protect the system. It has three states:

      • Closed: calls flow normally, failures are counted.
      • Open: too many recent failures. Calls fail immediately without touching the dependency, giving it room to recover and freeing your threads.
      • Half-open: after a break period, a trial call is allowed through. Success closes the circuit; failure opens it again.

With the breaker on, they fail in microseconds while it's open. Pair the breaker with a fallback, and users still see a useful (if slightly old) ETA instead of an error.

      Timeouts and deadline budgets

      A timeout must be shorter than the caller's timeout, or it's useless. If the user-facing request has a 3-second budget and it calls A (which calls B), B's timeout must leave A time to respond. Think in deadlines that shrink as they propagate, not fixed timeouts per hop. In .NET, pass the CancellationToken through every layer, so when the outer request is cancelled, all inner work stops too. gRPC propagates deadlines automatically.

      Bulkheads

      If one dependency can consume every connection or thread in your service, it can starve everything else. A bulkhead gives each dependency a separate, limited pool: at most 20 concurrent calls to the partner ETA service, at most 50 to the payment provider. When the ETA service hangs, only its 20 slots fill up; bookings keep working. HttpClient connection limits per named client and Polly's concurrency limiter both act as bulkheads.

      In .NET: Polly v8 pipelines

      Order matters in a pipeline: outer strategies wrap inner ones. Here the fallback is outermost (it catches everything), then the circuit breaker (it counts failures, including timeouts), then the timeout (innermost, on each call). Polly v8 also emits metrics for every strategy, which you can export with OpenTelemetry (Part 5) to see breakers opening in real time.

      In the real world: graceful degradation

      Decide in advance what each page does when each dependency is gone. The tracking page without the partner ETA service still shows the event history with "ETA temporarily unavailable." The booking page without the pricing service might allow booking at the last published rate for an hour. These are product decisions as much as technical ones; make them before the incident, not during it.

      Common pitfalls

      • No timeout at all. The default HttpClient.Timeout is 100 seconds, far too long for an interactive request.
      • Retries inside a breaker's sampling window making it trip on what are really a few failed user requests. Understand what each layer counts.
      • Fallbacks that hit the same broken dependency, or fall back to an expensive path that then overloads the database.
      • Hedging non-idempotent calls: two simultaneous POSTs. Hedge reads only.
      • Untested resilience. Inject faults in testing (Polly's chaos strategies can add latency and errors on demand) to prove the patterns actually work.

      4.5 Coordination: locks, leaders, consensus, and time

      Getting many machines to agree on one thing, when messages get lost and clocks disagree.

      About 35 minutesLevel: advanced1 simulator

      Some work must happen exactly once across the whole fleet: closing a voyage's booking window at the cutoff time, generating the nightly customs manifest, running the outbox relay without duplicates. With 10 instances, you need them to agree on who does it. That's coordination, and it's one of the genuinely hard problems in distributed systems.

      Distributed locks

      A distributed lock lets one instance at a time hold a named resource ("voyage-close:AE7-042"), stored somewhere shared: Redis, a database, or a coordination service. Three rules make them safe:

      1. Locks must expire (leases). If the holder crashes, the lock must free itself, so every lock has a time-to-live.
      2. Expiry creates a new danger. The holder might pause (a long GC, a VM migration) past its lease, while another instance takes the lock. Now two believe they hold it.
      3. Fencing tokens fix that. Each lock grant comes with an increasing number. The protected resource remembers the highest token it has seen and rejects writes with older ones. The paused instance wakes up, tries to write with token 33, and is refused because token 34 already wrote.

      Notice the conditional update. It's the database-level equivalent of a fencing check: the operation only succeeds from the expected prior state. Whenever you can, design so that correctness doesn't depend on the lock at all, and the lock is just an efficiency measure to avoid duplicate work.

      Leader election and consensus

      Rather than taking a lock for each job, a group of instances can elect one leader to do all coordinated work, with the others standing by. Electing a leader safely, so that there's never more than one per term even with failures and network splits, requires consensus. The most widely taught algorithm is Raft (used by etcd, Consul, and in Kubernetes' control plane via etcd). Its core ideas:

      • Time is divided into numbered terms. Each term has at most one leader.
      • The leader sends regular heartbeats. A follower that hears nothing for a randomized timeout becomes a candidate, increments the term, and asks for votes.
      • Each node votes at most once per term. A candidate with votes from a majority becomes leader.
      • Because two majorities of the same group always overlap, two leaders can't both win the same term. A node cut off in a minority can never become leader.

      In practice you rarely implement Raft yourself. You use a system built on it: Kubernetes leases (coordination.k8s.io) for leader election among pods, etcd or Consul for configuration, or a database that already runs consensus internally.       Time: why you can't trust clocks

      Each machine's clock drifts and is corrected by NTP, sometimes jumping backwards. Clocks on different machines can disagree by milliseconds, and occasionally much more. So:

      • Don't order events from different machines by wall-clock time when correctness depends on it. Last-writer-wins with skewed clocks silently keeps the wrong value (2.6).
      • Measure durations with a monotonic clock: in .NET, Stopwatch (or TimeProvider.GetTimestamp()), never DateTime.Now differences.
      • Use logical clocks for ordering: a Lamport clock is a counter incremented on each event and set to max(local, received) + 1 on each message, giving a consistent order of causally related events. Hybrid logical clocks combine wall time with a logical counter.
      • Inject time: TimeProvider (.NET 8+) makes time-dependent code testable, which matters for cutoffs and expiring reservations.

      Interview questions

      JuniorWhy does a distributed lock need an expiry, and what problem does that create?▶

      Without an expiry, a holder that crashes keeps the lock forever and the work never runs again. With an expiry, a holder that's merely paused (GC, slow I/O) can lose the lock without knowing, while another instance acquires it, so two instances act at once. Fencing tokens or idempotent, conditional operations protect against that.

      Likely follow-up: "Can't the holder just check it still has the lock before writing?" The pause can happen right after the check. Only the resource rejecting stale tokens closes the gap.
      MidWhy does Raft need a majority, and why does a 5-node cluster tolerate 2 failures but a 4-node cluster only 1?▶

      A majority ensures any two quorums overlap in at least one node, so two leaders can't be elected in the same term and committed data is never lost. 5 nodes need 3 for a majority, so 2 can fail. 4 nodes need 3 as well, so only 1 can fail: the extra node adds cost but no fault tolerance. That's why consensus clusters use odd sizes (3, 5, 7).

      Likely follow-up: "What happens to the 2-node side of a 3/2 split?" It can't elect a leader or commit writes; it stays unavailable until the partition heals. That's consensus choosing C over A.
      SeniorTen instances run a scheduled job that must close voyages at their cutoff time exactly once. Design it.▶

      Make correctness independent of coordination first: the closing operation is a conditional update (only Open → Closed) that's idempotent, with an audit event emitted through the outbox. Then add coordination for efficiency: either a leader (elected via a Kubernetes lease or a database/blob lease) runs the scheduler, or each instance tries a per-voyage lock and skips if held. Use TimeProvider and store cutoffs in UTC; compare using the database's clock (one clock) rather than each instance's. Monitor for voyages past cutoff still open, which catches a scheduler that silently stopped.

      Likely follow-up: "What if the leader dies right at the cutoff?" A new leader is elected within seconds and runs the pass; since the operation is idempotent and conditional, any partial work by the old leader is harmless.

      Snowflake in C#

      Human-facing references

      IDs for machines and references for people are different things. Customers read booking numbers over the phone and type them into forms, so a reference like BK-7Q4M-2KX9 (short, no ambiguous characters like 0/O and 1/I, with a check character) is better than a GUID. Container numbers already work this way: the ISO 6346 check digit on every chapter header in this guide catches most typing mistakes. Keep the internal ID as the primary key and the reference as a separate unique column.

      Common pitfalls

      • Exposing sequential IDs publicly. /bookings/1000412 invites people to try 1000413 (an insecure direct object reference if authorization is weak) and reveals your volume.
      • Storing GUIDs as strings. 36 bytes instead of 16, slower comparisons and bigger indexes. Use native uuid / uniqueidentifier columns.
      • SQL Server and UUIDv7. SQL Server sorts uniqueidentifier by a different byte order, so UUIDv7's time ordering isn't preserved there; EF Core's sequential GUID generator (the default for SQL Server keys) is designed for its ordering. PostgreSQL sorts UUIDv7 correctly.

      5.1 Observability

      Logs, metrics, and distributed traces with OpenTelemetry: being able to answer "what is happening, and why?" about a system you can't step through in a debugger.

      In a monolith on one server, you could read one log file.       OpenTelemetry in .NET

      OpenTelemetry (OTel) is the vendor-neutral standard for producing and exporting all three signals. .NET is unusually well integrated: the runtime's own System.Diagnostics.Activity (traces), System.Diagnostics.Metrics (metrics), and ILogger (logs) are the OTel APIs, and ASP.NET Core, HttpClient, gRPC, and many libraries already emit telemetry.       With Aspire

      An Aspire solution's ServiceDefaults project contains this OpenTelemetry setup already, and the Aspire dashboard shows logs, traces, and metrics for every service as soon as you run the AppHost. Recent Aspire releases have added persistent telemetry and run history to the dashboard, so you can compare runs. It's the fastest way to learn to read traces: build the saga from Part 4 and watch it.

      What to measure: golden signals and SLO alerts

      For every service, start with the four golden signals: latency (p50, p95, p99, separately for successes and errors), traffic (requests per second), errors (rate of failed requests), and saturation (how full the most constrained resource is: CPU, connection pool, queue depth, consumer lag). For message-driven services, add the age of the oldest unprocessed message.

      Alert on symptoms users feel, not on every cause. "CPU at 85%" isn't an incident if users are fine; "booking error rate is burning the monthly error budget 14× faster than sustainable" is. Burn-rate alerts tie alerts to the SLOs from 1.2: with a 99.9% SLO over 30 days, a burn rate of 14.4 sustained for one hour consumes 2% of the month's budget, which is worth paging someone. A slow burn (say 1 to 3×, sustained for days) becomes a ticket rather than a page. Checking two windows (e.g., 1 hour and 5 minutes) avoids alerting on blips while still resolving quickly once the problem stops.

      Common pitfalls

      • High-cardinality metric labels. Adding the container number or user ID as a metric tag creates millions of time series and a huge bill. Put high-cardinality values in traces and logs, not metrics.
      • Logging secrets and personal data. Tokens, passwords, full card numbers, and passport numbers end up in log stores with weak access control. Redact by design.
      • Broken propagation across messages. Traces stop at the broker unless the trace context is put into message headers and restored by the consumer. Most broker SDKs and Wolverine do this; check that yours does.
      • Alert fatigue. If most pages need no action, people stop responding. Every alert should be actionable and tied to user impact.
      • Sampling away the interesting traces. Random 1% sampling usually misses the rare slow or failed request. Tail-based sampling (in an OTel Collector) keeps all errors and slow traces.

      Likely follow-up: "What about dependencies, like the payment provider?" Monitor them for diagnosis, but page on your own user-facing SLO; if the provider's outage hurts users, your SLO alert fires anyway.

      5.2 Security

      Authentication, authorization, tokens, secrets, and the most common ways web systems get breached.

      About 40 minutesLevel: intermediate1 interactive token lab

      Security is a system design concern, not a feature you add later. Most breaches don't involve clever cryptography attacks; they come from missing authorization checks, misconfigurations, leaked secrets, and vulnerable dependencies. Design so the secure path is the default path.

      Authentication versus authorization

      • Authentication (AuthN): who are you? Proving identity, via a password plus a second factor, a passkey, a certificate, or a token from a trusted identity provider.
      • Authorization (AuthZ): what may you do? Deciding whether this identity may perform this action on this specific resource.

      Don't build authentication yourself. Use an identity provider (Microsoft Entra ID, Entra External ID for customers, Auth0, Keycloak, Duende IdentityServer) that speaks the standard protocols, and have your APIs validate the tokens it issues.

      OAuth 2.0 and OpenID Connect, in brief

      OAuth 2.0 is a framework for obtaining access tokens that grant limited access to an API. OpenID Connect (OIDC) adds identity on top: an ID token telling the client who the user is. The flows you'll actually use:

      FlowWhoBlueHarbor example
      Authorization code + PKCEUsers signing in to web, mobile, and single-page appsA shipper logs in to the customer portal
      Client credentialsMachine to machine, no userA partner's system calls the tracking API; internal services call each other
      Managed identity (Azure)Your Azure-hosted service calling Azure resourcesBooking API reads Key Vault and Blob Storage with no stored credentials

      The older "implicit" and "password" flows are deprecated in current OAuth guidance; don't use them in new systems.

      JWTs: what's inside a token, and why it can be trusted

      Access tokens are commonly JWTs (JSON Web Tokens): three Base64URL parts separated by dots. The header names the signing algorithm, the payload holds claims (who, for which API, until when, with which permissions), and the signature proves the issuer created exactly this header and payload. The payload is only encoded, not encrypted: anyone can read it. Security comes from the signature. Try tampering with one:

      Real systems usually use asymmetric signatures (RS256, ES256): the identity provider signs with a private key, and APIs verify with the public key, fetched automatically from the provider's metadata. APIs never hold a key that could create tokens.
      
  
  
      That last check is the one most often missing in real breaches: the API verifies the token, but never checks that this booking belongs to this customer, so changing the reference in the URL shows someone else's shipment. In multi-tenant systems, enforce tenant scoping centrally as well, for example with an EF Core global query filter on CustomerId, so a forgotten check doesn't leak data.
      

  
      Secrets
      
  
        
    
      • No secrets in code or config files. Not in appsettings.json, not in Git history. Use user secrets locally and a vault in deployed environments.
        • 
    
      • Prefer no secrets at all. With managed identities (Azure) or workload identity (Kubernetes), services authenticate to databases, storage, and Key Vault with platform-issued identities. Nothing to leak or rotate.
        • 
    
      • When you must have secrets (a partner API key), store them in Azure Key Vault or AWS Secrets Manager, load them through configuration, and rotate them.

      Common pitfalls
      
    
        
      
      • Putting sensitive data in JWT payloads. Anyone holding the token can read it.
        • 
      
      • Long-lived access tokens with no revocation. Keep access tokens short (minutes to an hour) and use refresh tokens, which can be revoked.
        • 
      
      • Storing tokens in browser localStorage for SPAs, where any XSS can steal them. Prefer the backend-for-frontend (BFF) pattern with HTTP-only, secure cookies.
        • 
      
      • Trusting the network. "It's internal, so no auth needed" is how one compromised service becomes a full breach. Authenticate service-to-service calls too (zero trust).

      Interview questions
      
  
      
    
      JuniorWhat's the difference between authentication and authorization? Where does a JWT fit?▶
      
      
        
      Authentication establishes who the caller is; authorization decides what they're allowed to do. A JWT access token is the result of authentication at an identity provider: a signed set of claims (subject, audience, expiry, scopes or roles) that the API validates on each request. The API then uses those claims, plus checks against the specific resource, to authorize.
      
        
      Likely follow-up: "Is a JWT encrypted?" Usually not, only signed. The payload is readable by anyone; the signature prevents modification.
      
      
      
    
      MidWhich OAuth flow for a partner's backend calling your API, and which for your single-page app?▶
      
      
        
      Partner backend, no user involved: client credentials. The partner authenticates as an application (ideally with a certificate or federated credential rather than a shared secret) and gets a token scoped to the tracking API. SPA with users: authorization code with PKCE, preferably through a backend-for-frontend that keeps tokens server-side and gives the browser an HTTP-only session cookie.
      
        
      Likely follow-up: "What does PKCE protect against?" Interception of the authorization code: the client proves it's the same party that started the flow using a one-time verifier.
      
      
      
    
      SeniorDesign authorization for a multi-tenant logistics platform where forwarders act on behalf of many shippers.▶
      
      
        
      Model relationships explicitly: a forwarder organization is granted access to specific shippers' data, possibly per operation (view tracking, create bookings). Tokens carry the caller's identity and organization; fine-grained permissions are evaluated server-side against a relationship store rather than stuffed into tokens (which would grow huge and go stale).
      
        
      Enforce in layers: the gateway checks authentication and coarse scopes; each service checks resource-level access with a shared authorization library or a policy service (relationship-based access control, in the style of Google Zanzibar, e.g., OpenFGA); the data layer applies tenant filters as a safety net. Cache permission checks briefly, audit every cross-tenant access, and fail closed if the policy service is unavailable for writes (possibly allow cached reads).
      
        
      Likely follow-up: "A shipper revokes a forwarder's access. How fast does it take effect?" Bounded by permission cache TTL and token lifetime; keep both short, or push revocation events to invalidate caches immediately.

      Database changes: expand and contract
      
  
      During any rolling or canary deploy, old and new code run at the same time against the same database. A migration that renames a column breaks the old version instantly. The fix is to split breaking schema changes into backward-compatible steps:

        2.

        3.

        4. 
    
      4. Contract: once no running version uses the old column, drop it.

      JuniorWhat's the difference between a container image and a container? Why use them?▶
      
      
        
      An image is an immutable package (app, runtime, dependencies, metadata); a container is a running instance of an image. Containers give consistency across environments, fast startup, efficient packing on hosts, and a standard unit for orchestrators to schedule, scale, and replace.
      
        
      Likely follow-up: "Why chiseled or distroless images?" Smaller attack surface (no shell or package manager), fewer vulnerabilities to patch, smaller downloads.
      
      
      
    
      MidCompare blue-green and canary deployments.▶
      
      
        
      Blue-green runs two full environments and switches all traffic at once: rollback is instant, but a bad release hits everyone until you switch back, and you need double capacity during the switch. Canary shifts traffic gradually and checks metrics at each step: a bad release only affects a small slice and can be rolled back automatically, but rollout takes longer and needs good metrics and enough traffic to judge. Many teams combine them: a green environment receiving canary traffic.
      
        
      Likely follow-up: "What do you compare during canary analysis?" Error rate, latency percentiles, and key business metrics (booking success) of canary versus baseline, over the same time window.
      
      
      
    
      SeniorYou need to split the Name column of 300 million shipper records into FirstName and LastName with zero downtime. Walk through it.▶
      
      
        
      Expand and contract. (1) Add nullable FirstName/LastName columns (a metadata-only change in modern PostgreSQL and SQL Server). (2) Deploy code that writes both the old and new columns on every write, and reads old. (3) Backfill in small batches (by key range, a few thousand rows per batch, throttled, resumable, off-peak) to avoid long locks and replication lag spikes. (4) Verify counts and sample data. (5) Deploy code that reads the new columns (behind a flag, so you can flip back). (6) Stop writing the old column. (7) Drop it in a later release once no running version references it.
      
        
      Likely follow-up: "What about read replicas and CDC consumers during the backfill?" Throttle to keep replication lag within limits, and make sure downstream consumers tolerate the new columns before step 5.

      Regions and availability zones
      
  
      A region is a geographic area (West Europe, Southeast Asia) containing several availability zones: physically separate data centers with independent power, cooling, and networking, a few milliseconds apart. Zones protect against a building-level failure; regions protect against a regional disaster and bring you closer to users.
      
  
        
    
      • Zone-redundant within a region is the baseline for production: app instances spread across zones, zone-redundant databases with synchronous replication (no data loss on zone failure), zone-redundant storage and caches. Cost: modest. Many managed services make this a checkbox.
        • 
    
      • Multi-region adds protection against losing an entire region, at significant cost and complexity: data replication across hundreds of milliseconds, failover decisions, and doubled infrastructure.
        • 
  
      

  
      RTO and RPO
      
  
      Disaster recovery planning starts with two numbers per system, set by the business:
      
  
        
    
      • RTO (recovery time objective): how long can it be down? "Bookings must be back within 1 hour."
        • 
    
      • RPO (recovery point objective): how much recent data can be lost? "At most 5 minutes of bookings."
        • 
  
      
  
      Lower numbers cost more. Use the planner to find the cheapest strategy that meets a requirement:

Tiering keeps DR affordable.
      
  
      

  
      The Well-Architected lens
      
  
      Both Azure and AWS publish a Well-Architected Framework for reviewing designs against pillars: reliability, security, cost optimization, operational excellence, and performance efficiency (AWS adds sustainability). It's a useful checklist for design reviews and a common interview frame: for any design, ask what each pillar says about it.
      

  
      
    
      Common pitfalls
      
    
        
      
      • Untested DR. A failover plan that's never been exercised usually fails when needed: expired credentials, missing config, DNS TTLs, capacity not available in the secondary region. Run game days.
        • 
      
      • Hidden single-region dependencies. The app fails over, but the identity provider config, container registry, or Key Vault lives only in the failed region.
        • 
      
      • Assuming capacity is available. During a regional outage, everyone fails over to the same neighboring regions. Reserved capacity or warm standby avoids the scramble.
        • 
      
      • Forgetting data residency. Replicating EU customer data to a non-EU region can breach regulations. Choose paired regions accordingly.

      JuniorWhat's the difference between RTO and RPO?▶
      
      
        
      RTO is the maximum acceptable downtime: how quickly the service must be restored. RPO is the maximum acceptable data loss, measured in time: how old the most recent recoverable data may be. A nightly backup gives an RPO of up to 24 hours; restoring it might take 3 hours, which is the RTO.
      
        
      Likely follow-up: "Which costs more to improve?" Both get expensive near zero, but zero RPO across regions is especially costly because it requires synchronous cross-region replication.
      
      
      
    
      MidWhat's the difference between availability zones and regions, and what does each protect against?▶
      
      
        
      Zones are separate data centers within one region, close enough (a few ms) for synchronous replication. They protect against failures of one facility: power, cooling, network, or a fire. Regions are far apart and protect against large-scale disasters or region-wide outages and allow serving users closer to them, but replication between them is asynchronous or slow. Zone redundancy is the production baseline; multi-region is a deliberate, costlier choice.
      
        
      Likely follow-up: "Which outage is more common?" Zone-level and service-level incidents are far more common than full regional loss, which is why zone redundancy delivers most of the reliability benefit for the cost.
      
      
      
    
      SeniorDesign BlueHarbor's booking platform to survive the loss of West Europe with RTO 15 minutes and RPO 1 minute.▶
      
      
        
      Warm standby in North Europe. Front Door routes all traffic to West Europe with health probes on both regions' gateways. Data: the booking database (Azure SQL or PostgreSQL) uses zone-redundant HA in the primary and an asynchronous geo-replica in North Europe (lag normally seconds, well under 1 minute); Service Bus geo-replication or an outbox design that can replay; blob storage geo-redundant; Redis rebuilt from source on failover (it's a cache). Compute: Container Apps in North Europe running at minimum scale with the same images, ready to scale out. All configuration, registry replication, Key Vault, and identity available in both regions.
      
        
      Failover runbook (automated where possible): confirm the regional outage, promote the database replica, switch Front Door priority, scale out compute, verify with synthetic transactions. Rehearse quarterly. Message idempotency (Part 3) makes re-delivered or replayed messages safe after failover.
      
        
      Likely follow-up: "Why not active-active?" Bookings need a single source of truth for capacity; multi-region writes would require conflict resolution on the hottest invariant in the system. Active-active is reserved for read-heavy parts like tracking.

        2. 
    
      2. Estimate (3–5 min). QPS for reads and writes, peak factor, storage over the retention period, bandwidth. Then say what the numbers mean: "Writes are small; the challenge is 20,000 reads per second at low latency."
        3. 
    
      3. API and data model (5 min). A few key endpoints with request and response shapes; the main entities and their keys; which store and why.
        4. 
    
      4. High-level design (8–10 min). Boxes and arrows covering every functional requirement end to end. Simple first, correct first. Walk one request through it.
        5. 
    
      5. Deep dives (15 min). Pick the two or three hardest parts (often the interviewer will steer): the bottleneck from your estimates, the consistency-critical path, the scaling cliff. This is where seniority shows: alternatives, trade-offs, failure modes, numbers.
        6. 
    
      6. Wrap up (5 min). Bottlenecks and single points of failure, what you'd monitor, what changes at 10x, what you'd build first.
        7. 
  
      

  
      
    
      Signals interviewers listen for
      
    
        
      
      • You ask before assuming, and you state assumptions out loud.
        • 
      
      • Your numbers drive your decisions ("Because writes are 40 per second, a single primary is fine").
        • 
      
      • Every choice comes with its cost ("Fan-out on write makes reads fast, but a celebrity post means 50 million writes").
        • 
      
      • You think about failure: what happens when this box dies?
        • 
      
      • You keep it simple until the requirements force complexity.
        •

      • Jumping to Kafka and Kubernetes in minute two. Tools without requirements look like memorization.
        • 
      
      • Going silent. Think out loud; the interviewer grades your reasoning, not just your final diagram.
        • 
      
      • Spending 20 minutes on requirements and never reaching deep dives.
        •

      Generating short codes
      
  
      With base62 characters (a–z, A–Z, 0–9), 7 characters give 627 ≈ 3.5 trillion codes, far more than 6 billion. How to pick them without collisions:
      
  
      ApproachProsCons

      Counter ranges per instance → scrambled → base62No collisions, no per-request coordination, unguessable after a reversible shuffleSmall gaps when an instance dies with an unused range (harmless)
      
    
      Random 7 chars, insert-if-absentSimple, unguessableCollision checks grow as the space fills (still rare at 0.2% full)

      301 or 302?
      
  
      A 301 Moved Permanently is cached by browsers forever, so repeat clicks never reach you: cheaper, but analytics undercount and you can't change or expire the link. A 302 Found (or 307) is not cached by default, so every click is counted. Most commercial shorteners use 302 and let the CDN cache the response briefly.
      
  
      Caching and scale
      
  
      Link popularity is extremely skewed: a small share of codes gets most clicks, so an L1 in-process cache plus Redis gives a very high hit ratio. Use negative caching for unknown codes (scanners probe random codes). The database is a simple key-value lookup by code: partition by code hash (Cosmos DB, DynamoDB, or sharded PostgreSQL).
      
  
  
      The multiplier must share no factors with 627 (whose prime factors are 2 and 31) for the scramble to be a one-to-one mapping. Any odd number not divisible by 31 works.

      • Abuse: scan target URLs against malware/phishing lists at creation and periodically; rate limit creation per user and IP.
        • 
    
      • Hot links: a viral link is just a hot cache key, served from L1 and the CDN.
        • 
    
      • Custom aliases: same table, insert-if-absent with a unique constraint; reserve words like api and admin.

      MidTwo users shorten the same long URL. Should they get the same code?▶

If storage savings matter for anonymous links, dedupe only those via a hash index. Say the trade-off and pick based on requirements.
      
      
      Likely follow-up: "How do you index 6 billion long URLs?" Index a hash of the URL, not the URL itself.
      
    
      SeniorHow do you keep redirects working if the primary database region fails?▶
      
      Redirects are read-only and tolerant of slight staleness, so serve them active-active from multiple regions with replicated read copies (Cosmos DB multi-region reads, or async replicas), plus CDN and Redis caching. Link creation can fail over more slowly (warm standby), since its availability target is lower. New links created just before a failover might be missing from a lagging replica for seconds; acceptable, or route reads of very new codes to the primary region.

      6.3 Distributed rate limiter
      
    
      Turning the algorithms from 3.5 into a shared service for a whole fleet, adding under 2 ms per request.
      
    
      About 25 minutesLevel: intermediate
      
  
      

  
      1. Requirements
      
  
      FunctionalNon-functional
      
    
      Limit requests per key (API key, user, IP) according to rulesAdds under 2 ms at p99
      
    
      Rules configurable without deploys (per plan, per endpoint)Accurate across all instances (global limits)
      
    
      Return 429 with Retry-After and quota headersHighly available; if it fails, the API must keep working
      
  
      
  
      2. Estimates
      
  
      • 1 million requests/s across the fleet → 1 million limiter checks/s.
      • 10 million active keys × ~50 bytes of state ≈ 500 MB: fits in a Redis cluster comfortably.
      • Conclusion: the challenge is latency and atomicity at very high QPS, not storage.
      

  
      3. High-level design
      
  

  
      4. Deep dives
      
  
      Atomicity: why a Lua script
      
  
      "Read tokens, compute refill, decrement, write back" as separate commands races between gateway instances (a lost update, as in 2.3). Redis runs a Lua script atomically, so the whole check is one round trip and one indivisible operation. Using Redis's own clock (TIME) avoids skew between gateway clocks.
      
  
  
      Scaling past one Redis
      
  
        
    
      • Shard by key across a Redis cluster: each key's state lives on one node, so scripts stay atomic.
        • 
    
      • Hot keys (one partner sending 50,000 req/s): give each gateway a local token allowance it refills from Redis in batches ("take 100 tokens at once"), trading a little accuracy for far fewer calls.
        • 
    
      • Multi-region: split each key's quota between regions and count locally (3.5), rebalancing periodically.
        • 
    
      • Failure: fail open to a per-instance in-memory limiter (ASP.NET Core's built-in one) so a Redis outage degrades fairness, not availability.
        • 
  
      

  
      Interview questions
      
  
      
    
      MidWhy not keep a per-key counter with INCR and EXPIRE?▶
      
      That's a fixed window, which works and is cheap, but it allows up to 2x bursts at window boundaries, and setting INCR and EXPIRE as separate commands can leave a key without expiry if the client dies between them. A token bucket or sliding window in one Lua script is accurate and atomic.
      
    
      SeniorRate limiting adds 1.5 ms to every request. The team wants it gone. Options?▶
      
      Batch token leases per gateway instance (most requests decided locally); run the check concurrently with routing rather than before it, rejecting before the backend call; colocate Redis in the same zone; use pipelining. Or accept approximate enforcement for low-risk tiers using only local limits, and strict global checks only for expensive endpoints. Measure the cost against what limiting protects.

      6.4 Chat application
      
    
      Millions of persistent connections, ordered delivery, receipts, presence, and offline users.
      
    
      About 35 minutesLevel: intermediate to advanced
      
  
      

  
      1. Requirements
      
  
      FunctionalNon-functional
      
    
      1:1 and group chats (up to 500 members)Delivery under 200 ms when both users are online
      
    
      Sent / delivered / read receiptsMessages never lost once acknowledged as sent
      
    
      Online presence, typing indicatorsOrder preserved within a conversation
      
    
      History on any device; push notifications when offline50 million daily users, 10 million concurrently connected
      
  
      
  
      2. Estimates
      
  
        
    
      • 50M users × 40 messages/day = 2 billion messages/day ≈ 23,000/s average, ~100,000/s peak.
        • 
    
      • ~150 bytes per message ≈ 300 GB/day ≈ 110 TB/year (before replication and media, which lives in blob storage).
        • 
    
      • 10 million concurrent connections at ~50,000 per gateway node ≈ 200+ gateway nodes.
        • 
    
      • Conclusion: the hard parts are connection management, routing between gateways, and a write-heavy message store.
        • 
  
      

  
      3. High-level design
      
  

  
      4. Deep dives
      
  
      Connections and routing
      
  
      Gateways hold WebSocket connections and nothing else; they're stateful only in which users are connected to them. When a user connects, the gateway writes user → gateway to a session map in Redis with a TTL refreshed by heartbeats. To deliver, the chat service looks up the recipient's gateway(s) (one per device) and publishes to that gateway's channel. Gateways scale horizontally; when one dies, its clients reconnect elsewhere and re-register. In .NET, SignalR with Azure SignalR Service can play the gateway role and handle the routing for you up to very large scales.
      
  
      Ordering and duplicates
      
  
        
    
      • Each message gets a per-conversation sequence number assigned by the chat service (one writer per conversation partition, e.g., an atomic counter or the partition's log offset). Clients display in sequence order and detect gaps ("fetch 1041–1043").
        • 
    
      • Clients attach a client message ID (UUIDv7). Retries after a dropped connection reuse it, and the server deduplicates: the idempotency key pattern from 3.2.
        • 
  
      
  
      Storage
      
  
      The access pattern is "append to conversation" and "read the latest N messages of a conversation." That fits a wide-column store partitioned by conversation_id and clustered by sequence (Cassandra, ScyllaDB, or Cosmos DB with conversation as the partition key). Very active conversations are bucketed by time to keep partitions bounded. Media goes to blob storage via signed URLs (2.7); the message holds a reference.
      
  
      Receipts and presence
      
  
      Receipts are tiny messages flowing back ("delivered up to seq 1043", "read up to seq 1040"), which batch naturally. Presence is expensive at scale: don't broadcast every online/offline flip to every contact. Keep last-seen with TTLs in Redis, and fetch presence lazily when a chat is opened, pushing updates only for open conversations.
      
  

  
      Interview questions
      
  
      
    
      MidHow do you guarantee message order in a group chat with members on different gateways?▶
      
      Assign order at a single point per conversation: the chat service partition owning that conversation assigns monotonically increasing sequence numbers when persisting. Delivery paths can reorder, so clients sort by sequence and request gaps. Don't rely on client timestamps or arrival order.
      
    
      SeniorA group has 100,000 members (a broadcast channel). What changes?▶
      
      Write-time fan-out to 100,000 recipients per message (receipts, unread counters, pushes) becomes too expensive. Switch to read-time: store once, members fetch on open; send pushes only to members who opted in, batched and rate limited; drop per-member delivered/read receipts in favor of aggregate view counts; deliver live updates only to currently connected members via group pub/sub. Same idea as the celebrity problem in news feeds (6.5).

      6.5 News feed
      
    
      Building every user's home timeline from the people they follow, fast, including when someone has 50 million followers.
      
    
      About 30 minutesLevel: intermediate to advanced1 simulator
      
  
      

  
      1. Requirements
      
  
      FunctionalNon-functional
      
    
      Publish posts (text, media)Home feed loads in under 200 ms
      
    
      Follow / unfollowNew posts appear in followers' feeds within a few seconds (eventual is fine)
      
    
      Home feed: recent posts from followed accounts, ranked300M daily users; reads vastly outnumber writes
      
  
      
  
      2. Estimates
      
  
      • 300M users × 10 feed loads/day ≈ 35,000 feed reads/s (peak ~150,000).
      • 300M × 0.5 posts/day ≈ 1,700 posts/s.
      • Average 200 followers, but a long tail up to 50M+. That skew is the whole problem.
      

  
      3. The core decision: fan-out on write or on read?
      
  
        
    
      • Fan-out on write (push): when someone posts, insert the post ID into every follower's precomputed feed (a capped list in Redis). Reading is a single cheap lookup. Writing costs one insert per follower.
        • 
    
      • Fan-out on read (pull): store posts once; when a user opens the feed, fetch recent posts from everyone they follow and merge. Writing is cheap; reading costs one query per followed account.
        • 
    
      • Hybrid: push for normal accounts, pull for celebrities (above some follower threshold), merged at read time. This is what large social networks have described doing.
        • 
  
      

  
      
    
      Fan-out simulator
      Interactive
      
    
      
      
      
        
      
        
      
        
      
      
      
      
      
      
      
    
      
  
      

  
      4. High-level design
      
  
  
      5. Deep dives
      
  
        
    
      • Feed cache: a Redis sorted set per user of post IDs scored by time (or rank), capped at ~800 entries. Only IDs: post bodies come from a post cache, so edits and deletes don't require rewriting millions of feeds.
        • 
    
      • Inactive users: don't fan out to users who haven't logged in for weeks. Build their feed on demand (pull) when they return.
        • 
    
      • Ranking: candidate generation (the cached IDs plus celebrity pulls), then a ranking stage scoring by relevance; cache the ranked page briefly.
        • 
    
      • Deletes and privacy: filter at read time (blocked users, deleted posts) because fanned-out IDs may be stale.
        • 
  
      
  

  
      Interview questions
      
  
      
    
      MidExplain the celebrity problem and the hybrid solution.▶
      
      With pure fan-out on write, one post by an account with 50 million followers means 50 million feed inserts, taking minutes and huge resources, and it happens on every post. With pure pull, every feed read queries hundreds of accounts. Hybrid pushes posts from normal accounts (cheap) and pulls only from the few celebrities a user follows, merging at read time. Reads stay fast; writes stay bounded.
      
    
      SeniorA user unfollows someone. Their posts still appear in the feed. How do you handle it?▶
      
      The cached feed contains IDs pushed earlier. Options: filter at read time against the current follow set (cheap if the follow list is cached as a set), and lazily remove stale entries; optionally run an async cleanup job removing that author's IDs from the user's feed. Read-time filtering is required anyway for blocks and deletes, so it's the primary mechanism.

      6.6 E-commerce checkout and flash sales
      
    
      Cart, inventory, order, and payment, without overselling, including when 200,000 people want the same 5,000 items at 10:00.
      
    
      About 30 minutesLevel: advanced
      
  
      

  
      1. Requirements
      
  
      FunctionalNon-functional
      
    
      Cart, checkout, order confirmationNever oversell limited stock
      
    
      Inventory reserved during checkout, released if abandonedNo double charges or duplicate orders
      
    
      Payment, then confirmation emailSurvive flash-sale spikes of 50–100x normal traffic
      
  
      

  
      2. High-level design
      
  

  
      3. Deep dives
      
  
      Inventory: reserve, don't decrement at "add to cart"
      
  
      Carts are wish lists; most are abandoned. Stock is reserved at checkout with an expiry (say 10 minutes), converted to sold on payment, and released on timeout or failure. The reservation itself must be atomic: the conditional update from 2.3 (UPDATE … SET reserved = reserved + n WHERE available - reserved >= n).
      
  
      Flash sales: protect the database
      
  
      200,000 people pressing "Buy" in the same second would melt a database row with lock contention. Layers of defense:
      
  
        
    
      1. Virtual waiting room: admit users to checkout at a controlled rate (a queue with position tokens). Fair, and turns a spike into a steady stream.
        2. 
    
      2. Stock tokens in Redis: load the 5,000 units into a Redis counter; each checkout atomically decrements. Below zero, sold out instantly, without touching the database. Winners proceed to create the reservation durably.
        3. 
    
      3. Async order creation: return "order received, processing" and complete the saga in the background.
        4. 
    
      4. Static, cached everything else: product pages from the CDN, no personalized calls on the hot path.
        5. 
  
      
  
  
      Idempotency end to end
      
  
      The "Place order" button generates an idempotency key used by the order API (3.2) and passed to the payment provider. Double-clicks, retries, and saga redeliveries all collapse into one order and one charge.
      

  
      Interview questions
      
  
      
    
      MidWhen should inventory be reserved: add to cart, checkout, or payment?▶
      
      Usually at checkout with a short expiry. At add-to-cart, abandoned carts would lock stock for hours; at payment, many users would pay for items already gone. For scarce items, reserving at checkout start with a visible timer ("held for 10 minutes") balances fairness and conversion.
      
    
      SeniorRedis says 0 units left but the database shows 3 unsold after the sale. Why, and is it a problem?▶
      
      Some winners claimed tokens in Redis but their durable reservation or payment failed, and the release back to Redis was lost (a crash between failure and release). The design deliberately errs toward underselling, never overselling. After the sale, reconcile from the database (the source of truth) and release the remaining units in a follow-up or to the waitlist.

      6.7 Payment system
      
    
      Moving money correctly: idempotency, unknown outcomes, double-entry ledgers, and reconciliation.
      
    
      About 30 minutesLevel: advanced
      
  
      

  
      1. Requirements
      
  
      FunctionalNon-functional
      
    
      Charge customers (cards, bank transfer) via payment service providers (PSPs)Correctness over availability: never charge twice, never lose a payment
      
    
      Refunds; payouts to partners (e.g., terminals, hauliers)Full audit trail; every balance explainable
      
    
      Balances and statements per accountMinimize PCI DSS scope: never store raw card numbers
      
  
      
  
      Volume is usually modest (thousands of transactions per second at most), so this design is about correctness, not scale.
      

  
      2. High-level design
      
  

  
      3. Deep dives
      
  
      A payment is a state machine
      
  
      Created → Authorizing → Authorized → Captured → (Refunded), plus Failed and the important one: Unknown. Every transition is persisted before and after calling the PSP.
      
  
      The unknown outcome
      
  
      You call the PSP; the connection times out. Was the card charged? You can't tell. Never blindly retry with a new request, and never assume failure. Instead: send the same idempotency key on retry (PSPs support this), or query the PSP for the payment by your reference, and rely on the PSP's webhook as a second source of truth. Payments stuck in Unknown are resolved by a background job and, ultimately, by reconciliation.
      
  
      Double-entry ledger
      
  
      Never store a balance as a mutable number that code updates. Record every movement as an immutable journal entry with lines that sum to zero: money moves from one account to another. Balances are sums of lines. Errors are fixed with new correcting entries, never edits. This makes every balance explainable and reconciliation possible.
      
  
  
      Reconciliation
      
  
      Daily, compare three views: your ledger, your payment state table, and the PSP's settlement report. Mismatches (a capture the PSP has but you don't, a fee that differs) go to an exceptions queue for automated fixes or finance review. Reconciliation is what catches the bugs everything else missed.
      

  
      Interview questions
      
  
      
    
      MidWhy use integer minor units instead of decimal or double for money?▶
      
      double can't represent most decimal fractions exactly, so sums drift. decimal is exact in .NET and fine within one process, but integer minor units are unambiguous across languages, databases, and APIs (most PSPs use them), and they force explicit rounding decisions (e.g., when splitting fees). Always store the currency with the amount; some currencies have 0 or 3 minor digits.
      
    
      SeniorThe PSP call times out, and your retry also times out. The customer is waiting. What do you do?▶
      
      Don't tell the customer it failed, and don't let them pay again with a new key. Mark the payment Unknown, show "We're confirming your payment," and resolve asynchronously: poll the PSP's status API by our reference, and accept the webhook when it arrives. The order stays pending with inventory held (with expiry). When resolved, continue the saga or release. If the customer retries, the same idempotency key ensures no second charge.

      6.8 Ride-sharing
      
    
      Real-time location at massive write rates, geospatial search, and matching one driver to one rider.
      
    
      About 35 minutesLevel: advanced1 interactive map
      
  
      

  
      1. Requirements
      
  
      FunctionalNon-functional
      
    
      Riders request a ride; see nearby drivers and ETAMatch within a few seconds
      
    
      Match a driver; driver accepts or declinesA driver is never assigned to two rides
      
    
      Live trip tracking; fare, surge pricing1 million active drivers, location every 4 s
      
  
      
  
      2. Estimates
      
  
      • 1M drivers ÷ 4 s = 250,000 location writes/s, each tiny and only the latest matters.
      • Ride requests: maybe 1,000–5,000/s at peak, each needing a "nearest drivers" query.
      • Conclusion: location is a high-rate, ephemeral, in-memory problem; trips are a lower-rate, durable, consistency problem. Two different stores.
      

  
      3. High-level design
      
  

  
      4. Deep dives
      
  
      Geospatial indexing
      
  
      "Drivers within 2 km" can't scan a million drivers. Divide the map into cells and index drivers by cell, so a query checks only the rider's cell and its neighbors. Common schemes: geohash (string prefixes of a Z-order grid; Redis GEO uses a similar encoding), Google's S2 (squares on a sphere), and Uber's H3 (hexagons, where every neighbor is equidistant; a C# port exists as pocketken.H3). Explore how cell size changes the work:
      

  
      
    
      Grid index explorer
      Interactive
      
    
      
      
      
        
      
      
      
      
      Tap the map to place the rider.
      
      
      
      
    
      
  
      

  
      Small cells mean few drivers checked per cell but many cells to search when drivers are sparse; big cells mean many irrelevant drivers per lookup. Real systems pick a resolution per city density and expand rings of neighbors until enough candidates are found.
      
  
      Location writes
      
  
      250,000 writes/s of "latest position" belong in memory: Redis GEO sets sharded by city or cell, or an in-process index in location service instances that own specific cells. Positions expire if a driver stops reporting. Raw location history for trips goes to a stream and cold storage asynchronously, never on the hot path.
      
  
      Matching without double assignment
      
  
      Matching ranks candidates by estimated time to pickup (road network ETA, not straight-line distance), then offers the ride to the best driver. The assignment must be atomic: a conditional update SET status = 'assigned', trip = @t WHERE driver = @d AND status = 'available', or a short lock per driver. If the driver declines or times out (10–15 s), offer to the next. This is the same "last slot" problem from 2.3, with drivers instead of TEU.
      
  
  
      Surge pricing
      
  
      Per cell, compare open requests with available drivers over a short window and compute a multiplier, smoothed to avoid oscillation. It's a streaming aggregation over the request and location streams, published to the pricing service every few seconds.
      

  
      Interview questions
      
  
      
    
      MidWhy not store driver locations in a relational database?▶
      
      250,000 updates per second of data where only the latest value matters would overwhelm a transactional database's write path, indexes, and logs for no benefit: losing a position is harmless because the next arrives in 4 seconds. An in-memory geo index (Redis GEO or sharded in-process structures) handles the rate and supports radius queries. Durable storage is reserved for trips and payments.
      
    
      SeniorTwo riders' requests both pick the same nearest driver at the same moment. Walk through what happens.▶
      
      Both matchers rank driver D first and try to assign. The atomic conditional assignment succeeds for one (D was available) and fails for the other (D is now assigned). The loser moves to its next candidate. To reduce collisions at scale, partition matching by area so one matcher instance owns a cell's drivers, or batch requests in short windows and solve the assignment for all of them together (better global ETAs).

      6.9 Video streaming
      
    
      Uploading, transcoding, and streaming video to millions of viewers on networks that change every second.
      
    
      About 30 minutesLevel: intermediate to advanced1 simulator
      
  
      

  
      1. Requirements
      
  
      FunctionalNon-functional
      
    
      Upload videos; process them for playbackPlayback starts in under 2 s; rare rebuffering
      
    
      Stream on any device and connection qualityMassive egress at low cost
      
    
      Resume where you left off; view countsUploads durable; processing can take minutes
      
  
      
  
      2. Estimates
      
  
      • 10 million concurrent viewers × 5 Mbps average = 50 Tbps of egress. No origin serves that: this is a CDN problem first.
      • Storage: each upload becomes ~6–8 renditions (240p to 4K); 1 hour of source can become 10–20 GB of outputs.
      

  
      3. High-level design
      
  

  
      4. Deep dives
      
  
      Transcoding pipeline
      
  
      Split the source into chunks (a few seconds each), transcode chunks in parallel across many workers into each rendition (resolution and bitrate), then package as HLS or DASH segments (CMAF lets one set of segments serve both).       7.1 Container track and trace
      
    
      Turning a stream of messy, late, duplicated events from terminals, vessels, and partners into one trustworthy timeline per container, following the DCSA standard.
      
    
      About 40 minutesLevel: advanced1 interactive normalizer
      
  
      

  
      This is BlueHarbor's running example, now designed properly. The hard part isn't serving lookups (Part 2 solved that). It's that the data comes from dozens of independent parties: terminals, rail operators, inland depots, partner carriers on shared vessels, and vessel position feeds, each in its own format, with its own delays and its own mistakes.
      

  
      The industry standard: DCSA Track & Trace
      
  
      The Digital Container Shipping Association, a neutral standards body founded by the largest ocean carriers, publishes open API specifications for track and trace, booking, the electronic bill of lading, and vessel schedules. Its event model is the natural target for any tracking platform. Three event families:
      
  
      FamilyAboutExample codes
      
    
      Equipment eventsWhat happened to a containerGate in, gate out, load, discharge, stuffing, stripping

It's available first to DCSA members and partners, with public release planned for the second half of 2027; many integrations still run 2.2, so a platform must support both.

      Normalization and deduplication

Timestamps may differ by seconds, location codes may use different conventions, and the container number may have a typo. The normalizer:
      
  
        
    
      1. Validates the container number with its ISO 6346 check digit (the same algorithm behind this guide's chapter headers) and rejects or quarantines invalid ones.
        2. 
    
      2. Maps source codes to the canonical model (EDI qualifiers, partner-specific codes, UN/LOCODEs and terminal SMDG codes).
        3. 
    
      3. Computes a natural key: container + event type + location + classifier + time bucketed to a tolerance window (e.g., 10 minutes). Events with the same natural key are the same fact; keep the most authoritative source.
        4. 
    
      4. Appends to the container's stream; never updates or deletes. Corrections are new events that supersede earlier ones.

        Late, out-of-order, and corrected events

        • Order by event time (when it happened), not arrival time; keep both.
          •

          •

          •

          •

That's the webhook design from 3.3: signed, retried, deduplicated by event ID, with a replay API for consumers recovering from outages.

        • Read scale: the 50,000 lookups/s design from the Part 2 exercise sits on top of the projections.
          • 
    
        • Observability per source: event lag (event time to received time) and volume per partner, with alerts when a terminal goes silent. Silence is the most common data-quality failure.
          • 
    
        • Raw archive: keep every inbound message as received, so mapping bugs can be fixed and history replayed.

        MidThe same gate-in arrives from the terminal and from a partner carrier, 3 minutes apart. How do you avoid showing it twice?▶

        SeniorA terminal had a mapping bug for a week: all its discharge events used the wrong location code. How do you fix history?▶
      
        Because raw messages are archived and the store is event-sourced, fix the mapping, then replay that terminal's raw messages for the affected window through the corrected normalizer, emitting correction events that supersede the wrong ones (never editing in place). Rebuild projections for affected containers, and suppress customer notifications for corrections that don't change customer-visible state, or send a single "corrected" notice. Add a contract test for that terminal's mapping.

        7.2 Reefer and smart container telemetry
        
    
        Streaming temperature data from 500,000 refrigerated containers, detecting real excursions without crying wolf, and surviving ships that go offline for hours.
        
    
        About 35 minutesLevel: advanced1 interactive detector
        
  
        

  
        Refrigerated ("reefer") containers carry fruit, vaccines, seafood, and pharmaceuticals at precise setpoints. A few degrees for a few hours can spoil a $200,000 cargo. Modern reefers and "smart" containers report temperature, humidity, power status, door openings, and location through vessel gateways, satellite, or cellular networks. DCSA's 2026 roadmap explicitly expanded tracking to reefer and IoT data, and Track & Trace 3.0 includes those event types.
        

  
        1. Requirements and estimates
        
  
          
    
        • 500,000 reefers × a reading every 15 minutes = 48 million readings/day ≈ 560/s steady (1.4), with bursts when a ship regains connectivity and uploads hours of buffered data.
          • 
    
        • Detect excursions and alert the cargo owner and operations within 5 minutes of the data arriving.
          • 
    
        • Keep raw readings 90 days, aggregates for years; produce a temperature log per shipment for claims and pharma compliance.
          • 
  
        

  
        2. High-level design
        
  

  
        3. Deep dives
        
  
        Excursion detection that people trust
        
  
        Raw thresholds generate floods of false alarms: a door opens during inspection, a defrost cycle briefly warms the air, a sensor glitches for one reading. Operations staff learn to ignore the alerts, then miss the real one. A good detector uses:
        
  
          
    
        • Tolerance bands around the setpoint (e.g., ±2 °C), per commodity.
          • 
    
        • Minimum duration: out of range for longer than N minutes, not one reading.
          • 
    
        • Hysteresis: once an excursion opens, it closes only when the temperature is back well inside the band, so a value hovering at the edge doesn't flap open/closed.
          • 
    
        • Context: suppress during known defrost cycles or when power is off at a terminal (that's a different alert).
          •

Consumer lag and oldest-unprocessed-reading age are the health signals.

        7.3 Ocean booking with capacity and overbooking
        
    
        Selling space on vessels that sail on fixed schedules: multi-dimensional capacity, multi-leg routes, contract allocations, and deliberate overbooking.
        
    
        About 40 minutesLevel: advanced1 simulator
        
  
        

  
        Every concurrency lesson in this guide was rehearsed on "the last 3 TEU." Here's the full system. An ocean booking reserves space for containers on a specific voyage, often across several legs (Shanghai → Singapore on one vessel, transshipment, Singapore → Rotterdam on another). DCSA's Booking 2.0 standard defines the booking request, confirmation, amendment, and notification flows that carriers expose to shippers and forwarders.
        

  
        1. Requirements
        
  
        FunctionalNon-functional
        
    
        Request, amend, cancel bookings; confirm or rejectCapacity limits enforced exactly, including the overbooking allowance
        
    
        Multi-leg routes with transshipmentAll legs reserved or none (atomic from the customer's view)
        
    
        Contract allocations per customer per weekPeak-season surges of 20x before Lunar New Year
        
    
        Notifications to customers on status changesDecision within seconds for standard cargo; special cargo may need human review
        
  
        

  
        2. Capacity is multi-dimensional
        
  
        A vessel's capacity isn't one number. A booking must fit all of these at once on every leg:
        
  
          
    
        • Slots in TEU (a 40-foot container uses 2 TEU).
          • 
    
        • Weight: a ship can run out of deadweight before slots when carrying heavy cargo.
          • 
    
        • Reefer plugs: limited powered slots for refrigerated containers.
          • 
    
        • Dangerous goods: limited positions by hazard class, with segregation rules.
          • 
    
        • Allocations: space promised to contract customers or partner carriers (vessel sharing agreements), which others can't take until it's released.
          • 
  
        
  
        All dimensions must be checked and reserved atomically per leg. The atomic conditional update from 2.3 extends naturally: one statement per leg with every dimension in the WHERE clause, all legs in one database transaction (they live in the same voyages database).
        

  
        3. Overbooking on purpose
        
  
        A share of bookings never show up: the cargo isn't ready, the shipper double-booked with another carrier, or the order was cancelled. Sailing with empty slots is lost revenue, so carriers accept more bookings than physical capacity. When more cargo shows up than fits, some is "rolled" to the next sailing, which annoys customers and costs money. The overbooking level is a business optimization, but the system must enforce whatever limit is chosen exactly.

        Where to put each container in a stack so it can be retrieved without digging, and how a terminal operating system keeps physical and digital reality in sync.

        A container terminal is a physical system with a digital twin, the terminal operating system (TOS). It plans berth windows for arriving vessels, assigns quay cranes, decides a yard position for every container, and dispatches straddle carriers or trucks, all while the plan keeps changing because vessels arrive late and trucks don't follow appointments.
        

  
        The core problem: rehandles
        
  
        Containers are stacked several high. If the box you need is under three others, the crane must move those three first: rehandles (reshuffles) cost time and fuel, and they slow every truck and vessel waiting.         • Real-time decisions (where does this truck's box go, now?) need answers in milliseconds from the current yard state: an in-memory model of the yard, updated from equipment events.
          • 
    
        • Batch optimization (pre-marshalling overnight, berth plans for next week) can take minutes on separate compute, publishing new plans the real-time layer then follows.
          • 
    
        • Reality wins: equipment reports (via telemetry, OCR at gates, crane sensors) are the source of truth for positions. When the digital and physical yard disagree (a box isn't where the system thinks), the system raises an exception rather than trusting the plan.
          • 
  
        

  
        Berth allocation
        
  
        Berths are a scarce, time-sliced resource: each vessel needs a quay segment long enough for its length for a time window based on its crane workload. Plans are built weeks ahead from schedules and revised constantly from ETA updates (7.5's AIS data feeds this). It's a scheduling problem much like room booking with variable sizes, with the same consistency rule: no two vessels can hold the same quay meters at the same time, enforced atomically when a window is confirmed.
        

  
        Messages in and out
        
  
        Terminals still exchange most data with carriers through EDIFACT messages: BAPLIE (bay plans: where every container sits on the vessel), COPRAR (load and discharge orders), COARRI (load/discharge reports), and CODECO (gate in/out reports). These feed and are produced by the TOS. They're the raw inputs to track and trace (7.1), and 7.6 shows how to integrate them.
        
  

  
        Interview questions
        
  
        
    
        MidWhy separate real-time placement decisions from batch optimization?▶
      
        They have different latency budgets and inputs. A truck at the gate needs an answer in milliseconds from the current state; an overnight yard re-organization can take minutes and consider everything. Running heavy optimization on the request path would make the gate slow and fragile; using only greedy real-time rules would leave efficiency on the table. The batch layer produces plans and parameters; the real-time layer applies them with fallbacks when reality deviates.
        
    
        SeniorThe TOS believes a container is in block C, bay 12, tier 3, but the crane driver finds a different box there. What should the system do?▶
      
        Treat the physical observation as truth and the digital record as suspect: record an inventory discrepancy event, mark both positions uncertain, trigger a search or scan task (OCR or RFID on nearby equipment), and re-plan the current move. Avoid silently "fixing" the record, because the discrepancy may indicate an earlier misplaced move affecting other boxes. Track discrepancy rates per block and equipment as a data-quality metric. It's the event-sourcing mindset applied to a physical world: append observations, derive state, and investigate conflicts.

        7.5 Vessel tracking with AIS
        
    
        Ingesting position broadcasts from the world's fleet, turning noisy coordinates into reliable arrival and departure events, and feeding ETAs.
        
    
        About 30 minutesLevel: advanced1 interactive detector
        
  
        

  
        Ships broadcast their identity, position, speed, and course over the Automatic Identification System (AIS), originally for collision avoidance. Shore stations pick up broadcasts near coasts; satellites cover the open ocean, with more delay. Data providers aggregate both and sell feeds. For a carrier, AIS answers "where is the vessel, and when will it arrive?" independently of what partners report, which makes it a powerful cross-check for track and trace (7.1) and berth planning (7.4).
        

  
        1. Characteristics and estimates
        
  
          
    
        • Moving commercial ships report position every few seconds (more often when fast or turning), much less often at anchor; static and voyage data (destination, draught, declared ETA) every few minutes.
          • 
    
        • A global feed can carry tens of thousands of messages per second, and the same broadcast is often heard by several receivers, so duplicates are normal.
          • 
    
        • Data is noisy: GPS jitter, wrong destinations typed by crews, gaps of hours over open ocean, occasional spoofing.
          • 
    
        • BlueHarbor only needs its own and partners' vessels (a few hundred) in detail, but often wants global context for congestion and port wait times.
          • 
  
        

  
        2. High-level design
        
  

  
        3. Deep dives
        
  
        From positions to events: geofences with hysteresis
        
  
        "The vessel arrived at Rotterdam" isn't in the AIS data; you infer it. Define port and berth areas as polygons (geofences), and emit an actual arrival transport event when a vessel enters. Naively, the first position inside the polygon is the arrival. In practice, GPS jitter near the boundary makes vessels "enter" and "leave" repeatedly, and ships waiting at anchor just outside drift across the line. Require several consecutive positions inside and low speed before declaring arrival:

        Interactive
        
    
        
      
        
        
        
      
        
      
        
      
      
        
    
        
  
        

  
  
        Production systems refine this with port-specific polygons for anchorages versus berths, navigational status in AIS messages, and a cool-down after departure so one call doesn't produce several arrivals. Use a spatial index (2.5's cells or an R-tree in NetTopologySuite) when checking thousands of geofences.
        
  
        ETA prediction
        
  
        Crew-entered ETAs in AIS are often stale. A better ETA combines the remaining route distance (along shipping lanes, not a straight line), recent speed, typical waiting time at the destination's anchorage (learned from history of other vessels' arrival-to-berth times), and the berth plan (7.4). Publish it as an estimated arrival event, update it as conditions change, and only notify customers when the change is material (say more than 6 hours), to avoid spam.
        
  
        Storage
        
  
        Latest position per vessel in memory or Redis (a map shows thousands of ships). Full tracks in a time-series store, downsampled for older data (keep a point every few minutes at sea, full resolution near ports). Deduplicate messages heard by several receivers on (MMSI, timestamp, position) before storing.
        

  
        Interview questions
        
  
        
    
        MidWhy not trust the ETA a ship broadcasts in its AIS voyage data?▶
      
        It's typed manually by the crew and often not updated after delays, weather, or port congestion. It's a useful input but not authoritative. Derive ETAs from actual position, speed, route distance, and learned port waiting times, and treat the crew ETA as one feature among several.
        
    
        SeniorA vessel goes silent for 18 hours in mid-ocean. What does your system show and do?▶
      
        Show the last known position with its age clearly, and a dead-reckoned estimate (last speed and course along the planned route) visually marked as estimated. Keep the ETA estimate but widen its uncertainty. Don't emit false events or alarms just because of a coverage gap; alert only if silence exceeds what's normal for that route segment (learned from history), which could indicate equipment failure or spoofing. When positions resume, reconcile: discard the dead-reckoned path in favor of actual data and update the ETA.

        Design principles
        
  
          
    
        • Canonical model in the middle. With N partners and M internal systems, point-to-point means N × M mappings; a canonical model needs N + M. Use DCSA's models as the canonical shape where they exist.
          • 
    
        • Configuration over code. Partners use different EDIFACT versions, qualifiers, and code lists. Keep partner-specific mappings in versioned configuration, so onboarding partner #312 doesn't need a deploy.
          • 
    
        • Archive raw, always. Every inbound file stored exactly as received, with its hash, so you can prove what a partner sent and replay after fixing a mapping (7.1's history fix).
          • 
    
        • Idempotency. Partners resend files. Deduplicate by interchange control reference plus partner, and downstream by event natural keys.
          • 
    
        • Per-partner observability. Volume, error rate, and "last message received" per partner and message type. A partner going silent is the most important alert.
          • 
    
        • Acknowledgements. EDIFACT CONTRL and X12 997/999 functional acknowledgements tell partners whether their messages were accepted; generate them automatically.
          • 
  
        
  
  
        Real EDIFACT messages have more segments, versions (D.95B, D.00B…), and implementation guides that vary by partner and community (SMDG publishes terminal-related ones). Use a mature parser library for production and validate against each partner's guide.
        

  
        Interview questions
        
  
        
    
        MidWhy introduce a canonical data model instead of mapping each partner directly to each internal system?▶
      
        Point-to-point integration grows as N partners × M systems, and every internal change touches many mappings. A canonical model reduces it to N + M: each partner maps to the canonical format once, each internal system consumes it once. It also gives one place for validation, deduplication, and lineage. The cost is designing and governing the model; adopting an industry standard (DCSA) for it reduces that cost.
        
    
        SeniorA major terminal changes its CODECO format without notice on a Friday night. Thousands of messages start failing. What happens in a well-designed hub?▶
      
        Failed messages are archived raw and land in the exceptions queue (nothing is lost); per-partner error-rate alerts fire within minutes. Downstream, track and trace sees a gap for that terminal rather than wrong data. On-call adjusts the partner's mapping configuration (no deploy needed), validates it against a sample in the exceptions UI, then replays the failed messages from the archive in order. Idempotent processing makes replay safe. Afterwards, add a contract test for the new format and talk to the partner about change notification.

        Final design exercise
        
  
        
    
        The brief
        
    
        BlueHarbor acquires a smaller carrier with its own booking system, tracking, and 140 EDI partners. Leadership wants one customer portal within 6 months, one booking flow within 12, and no customer-visible outage during the migration. Design the integration and migration plan.
        
  
        
  
        WalkthroughOpen after you've sketched your answer▶
    
        
      
        Months 0–6, one portal (read side first). Connect the acquired carrier's systems to BlueHarbor's integration hub as just another partner: their tracking events and bookings flow in as canonical events (7.6). Track and trace (7.1) ingests them with a source priority, so one customer portal shows both fleets. Authentication federates both identity providers (5.2) so customers keep their logins. The portal routes through the gateway (YARP) to whichever booking system owns a booking, behind one UI (strangler fig, 4.1).
        
      
        Months 6–12, one booking flow (write side). New bookings for the acquired fleet's voyages go through BlueHarbor's booking service, with the acquired carrier's capacity exposed through an adapter (a saga step like a partner leg, 7.3). Migrate voyages to BlueHarbor's capacity service route by route, with expand/contract-style dual running and reconciliation reports (5.3, 6.7 mindset). Existing bookings stay in the old system until they complete, or are migrated in batches by voyage.
        
      
        Partners. The 140 EDI partners keep sending as they do today; mappings move into the hub's configuration one partner at a time, with raw archives and replay as the safety net. No partner is forced to change in month one.
        
      
        No visible outage. Canary routing per customer segment (5.3), feature flags per route, dashboards comparing the old and new paths (5.1), and a tested rollback at each step. Data reconciliation jobs run daily and block the next step if they find mismatches.
        
      
        Trade-offs to state. Running two systems in parallel for months costs money and complexity, in exchange for avoiding a risky big-bang cutover. Read-side unification first gives customers visible value early while the harder write-side migration proceeds safely.

        Cheat sheets
        
  
        Part 1: Foundations
        
  
        
    
        The design loop
        • Clarify, estimate, API and data
        • High level, deep dive
        • Failure modes, evolve
        • Always state the trade-off
        
    
        Availability
        • 99.9% ≈ 8.8 h down a year
        • 99.99% ≈ 53 min a year
        • Series: multiply
        • Redundant: 1 − (1 − a)n
        
    
        Latency
        • Use p50, p95, p99, not averages
        • RAM ~100 ns, SSD ~100 µs
        • Same region ~0.5 ms, ocean ~100+ ms
        • Fresh HTTPS: 3 RTT (2 with QUIC)
        
    
        Estimation
        • 1 day ≈ 105 s
        • 1M/day ≈ 12/s
        • Peak = 2–10x average
        • Storage × retention × copies
        
    
        Little's Law
        • In flight = rate × time
        • Latency spikes become capacity problems
        • Pool total = instances × pool size
        
    
        Stateless .NET checklist
        • Shared Data Protection keys
        • Session and cache in Redis
        • Files in blob storage
        • Jobs in workers, not every instance
        • Forwarded headers, live and ready checks
        
  
        
  
        Part 2: Building blocks
        
  
        
    
        Load balancing
        • Round robin ignores load
        • Least requests / power of two adapt
        • Active + passive health checks
        • Keep health checks shallow
        
    
        Caching
        • Cache-aside by default
        • Write DB, then invalidate
        • Always keep a TTL
        • Stampede: coalesce, jitter
        • HybridCache: short L1, Redis L2
        
    
        Databases
        • Relational first, unless a pattern demands otherwise
        • Composite index: order matters
        • Sequential keys (UUIDv7)
        • Watch for N+1
        
    
        Concurrency
        • Atomic conditional UPDATE when possible
        • Optimistic: version column + retry
        • Pessimistic: FOR UPDATE, beware deadlocks
        • Write skew needs Serializable
        
    
        Replication
        • Async: fast, can lose recent writes
        • Lag breaks read-your-writes
        • W + R > N for overlap
        • Replicas aren't backups
        
    
        Sharding
        • Partition key: even spread + co-located queries
        • hash % N remaps ~all keys
        • Consistent hashing moves ~1/N
        • Shard late; let the DB do it
        
    
        CAP / consistency
        • During a partition: C or A
        • Otherwise: latency or consistency
        • Choose per operation
        • Session is a good default
        
    
        Blobs and CDN
        • Files in blobs, metadata in DB
        • Signed URLs, minutes, one object
        • Fingerprint assets, cache forever
        • private, no-store for user data
        
  
        
  
        Part 3: Communication
        
  
        
    
        API styles
        • REST for public and partner APIs
        • gRPC between internal services
        • GraphQL for varied UIs, with cost limits
        • ProblemDetails for errors
        
    
        API contracts
        • Cursor pagination for big or changing lists
        • Additive changes are safe
        • Version only to break; sunset with data
        • OpenAPI diff in CI
        
    
        Idempotency and retries
        • Idempotency key + result in same transaction
        • Retry only transient + idempotent
        • Exponential backoff + jitter + cap
        • Retry at one layer
        
    
        Real time
        • SSE for one-way (native in .NET 10)
        • WebSockets/SignalR for two-way
        • Backplane or Azure SignalR to scale
        • Webhooks: HMAC, retries, replay, SSRF checks
        
    
        Messaging
        • Queue: one consumer per message
        • Topic: copy per subscription
        • Stream: replayable log, partitions
        • At-least-once + idempotent consumer
        • DLQ for poison messages
        
    
        Rate limiting
        • Token bucket per API key
        • 429 + Retry-After
        • In-memory limits are per instance
        • Bound every queue; shed low priority
        
  
        
  
        Part 4: Distributed architecture
        
  
        
    
        Service boundaries
        • Modular monolith first
        • Split by business capability
        • Each service owns its data
        • Strangler fig to extract
        
    
        Sagas
        • Local transactions + compensations
        • Irreversible steps last
        • Expiring holds, deadlines
        • Orchestrate processes, choreograph reactions
        
    
        Outbox / inbox
        • Message row in same transaction
        • Relay publishes, then marks sent
        • Inbox dedupes by message ID
        • Or CDC (Debezium)
        
    
        Events and CQRS
        • Commands ask; events state facts
        • Event-carried state avoids call chains
        • Read models are eventually consistent
        • Event sourcing: history is the truth
        
    
        Resilience
        • Timeouts on every call
        • Breaker: closed, open, half-open
        • Bulkhead per dependency
        • Fallbacks decided in advance
        • Hedge reads only
        
    
        Coordination and IDs
        • Locks need leases + fencing tokens
        • Majority quorum; odd cluster sizes
        • Don't order by wall clocks
        • UUIDv7 default; Snowflake for 64-bit
